# Подготовка исходных данных

Вход из плагина открывает настройки проекта без запуска подготовки. Старый
параметр `open=editor` не даёт разрешения на расчёт. Распознавание и сохранение
его предложений не нажимают основное действие за пользователя. Только нажатие
«Подготовить» начинает непрерывный сценарий до карты; уход и отмена снимают
локальное намерение продолжить.

`useSourcePreparation` владеет запросами проекта/паспортом/статусом, формой RHF и
переходом на карту. `usePreparationCommit` владеет командой сохранения настроек и
запуска. `readPreparationEvidence` проверяет восстановление по фактам текущего
API; он не выполняет запись.

`usePreparationCompletion` владеет отдельной фазой после `completed`: читает
актуальный проект через общий `savedProjectQuery`, проверяет источник, версию
и доступность подготовленного снимка, затем открывает карту. Завершение
расчёта само по себе не служит командой навигации. Пока идёт чтение, основное
действие показывает «Открываем подготовленную карту». При ошибке доступно
«Повторить открытие карты»: выполняется только GET, расчёт повторно не
запускается. Поздний ответ для другого проекта и ответ после ухода не меняют
текущий экран. Физическая подготовка аналогично сохраняет квитанцию до свежего
чтения. Если её запустило основное действие, сценарий после чтения продолжает
расчёт и открывает карту. Для этого исходник и назначения должны совпасть с
начатым действием, а выбранная граница — допускать расчёт. Отмена снимает
намерение продолжить; чтение истории при повторном открытии его не создаёт.
Кешированное завершение перепроверяется при новом открытии: перед переходом
сверяются готовность и точная версия прочитанной публикации. Просмотр исходных
данных не возобновляет старую операцию из кеша; восстановление активной работы
начинается после свежего чтения журнала.

`useLayerRecognition` владеет первоначальным чтением, SSE-наблюдением и явным
продолжением распознавания. Для активной задачи открывается один поток событий;
периодических GET нет. Серверный результат остаётся в TanStack Query;
подтверждение назначений принадлежит сценарию подготовки. Запрос и поздний
ответ связаны с проектом, идентичностью исходника и его SHA. Сбой чтения либо
потерянный ответ команды требует GET состояния, а не повторного POST.
Продолжение допустимо после прочитанного `failed` для текущего исходника.
Автоматических повторов команды нет даже при включённом глобальном retry.
Локальные запросы используют `networkMode: always`.

Границы `surface_boundary` сохраняют категорию без фиктивной физической роли:
`kind=ignore`, `confirmed=false`. `isBoundaryTopologyIntent` отделяет это
намерение подготовки от очереди физических назначений. Таблица показывает
«Граница для замыкания», сводка считает такие слои отдельно. Подтверждённое
исключение и назначенная физическая роль не превращаются в это намерение.

Слой 0 разбирается в существующей очереди объектов. Выбор роли хранится в
черновике выбранного экземпляра и применяется явно. Запись передаёт source,
SHA геометрии, SHA захвата и ожидаемую ревизию проекта; весь слой не
подтверждается. Смена роли сохраняет линейное толкование, если оно уже выбрано.
Обозначение снимает физическую роль. Восстановление потерянного ответа сверяет
также `kind` и выполняет чтение без повторного POST. Сохранённая роль видна
при повторном открытии очереди.

Линейная интерпретация доступна каноническим кривым AutoCAD, включая замкнутые
полилинии. Для HATCH, REGION, SOLID и 3DFACE действие отключено; физическая роль
и справочная интерпретация доступны.

При обрыве SSE интерфейс показывает неизвестный статус и снимает анимацию.
Нативный `EventSource` может восстановить соединение и получить актуальный
снимок; корректное событие снимает ошибку без новой команды. Пользователь также
может явно прочитать статус. Завершённый результат, смена исходника или уход
с экрана закрывают подписку. Таймер прошедшего времени работает локально.

`layerRecognitionOptions` задаёт один ключ и политику чтения для подготовки и
рабочей карты. Режим `discover` использует существующий GET, который может
создать первое задание; `observe` вызывает отдельный `/status`, читающий только
существующее задание, checkpoint или результат. Ответ `null` означает отсутствие
наблюдаемой работы и не запускает распознавание. При повторном открытии документа
всегда читается актуальный статус; кешированный `failed` не разрешает повторную
команду до завершения этого чтения. Таймаут и AbortSignal принадлежат API-клиенту.

Состояние распознавания находится над сворачиваемыми разделами обоих документов.
`sourceRecognitionProgressInput` передаёт одну основу состояния кнопке хедера,
попапу и индикатору: чтение или запуск видны до получения серверной задачи.
`recognitionProgress` различает чтение, неизвестный результат запроса, первый
проход, завершение, приостановку, запись назначений и готовый результат.
`processed_count` измеряет только первый проход. Текущая задача берётся из
`stage`; первый проход и уточнения имеют собственные `stage_processed_count`
и `stage_total_count`. `active_layer_ids` связывает подпись с реальными слоями
текущего запроса. Этап `saving` показывает «Сохраняем предложения» без
выдуманного процента. Завершённый результат использует общие `processed_count`
и `total_count`, а не счётчик последней записи этапа. Для результата без указанного
этапа сохраняется состояние
ожидания после завершения первого прохода. Отдельный статус записи назначений
основан на текущей мутации, а не на вычисленном желании автоматического
применения. Кнопка хедера показывает фазу и счётчик с собственным объёмом этапа.
В попапе сводка разделяет принятые назначения, границы для замыкания и слои для
проверки; длительность и причина отказа раскрываются в «Подробностях».
Нижняя сетка содержит «Проверить слои» либо «Открыть слои» и доступное действие
восстановления. Ширины и высоты действий совпадают, на узкой панели сетка
переходит в одну колонку. Ошибка и завершение снимают анимацию.

`WorkspaceRecognitionActivity` наблюдает тот же результат на карте, включая
холодное открытие приложения. Он выполняет начальное чтение и наблюдает активную
задачу через SSE. Ошибка чтения или потока видима как недоступный статус.
Действие открывает исходные данные через существующий `leaveWorkspace`, сохраняя
политику ухода с черновиком. Observer не подтверждает назначения и не выполняет
POST. Автоматическое применение по-прежнему принадлежит форме подготовки;
перенос этой записи на backend является отдельным изменением контракта.

Backend сохраняет намерение запуска и принятые группы обоих проходов в
локальном checkpoint до публикации ответа. После перезапуска требуется явное
продолжение оставшихся групп; успешные уточнения повторно не отправляются.
Сбой проверки спорных слоёв сохраняет первичную разметку и оставляет задачу
`failed`, без ложного завершённого кеша. Ключ включает признаки обоих проходов
и основание локальных семантических сведений.

Политика `review_policy.py` и `autoAcceptRecognizedLayers` проверяет состав слоя
для новых и сохранённых предложений. Положительные количества известных
размерных классов AutoCAD и атрибутов подтверждают `annotation`; примесь LINE,
LWPOLYLINE, INSERT или неизвестного класса не допускает автоматического
исключения. Явное имя «Подписи» не заменяет проверку состава. Подтверждённое
ручное назначение сохраняется. Эта политика не назначает инженерные
характеристики и не меняет геометрию.

```text
Форма → PUT mappings → подтверждённая версия → POST geometry
                                               ↓
                              GET operation → SSE → completed
                                                       ↓
                                          GET project → карта

Потерянный ответ запуска → GET project → GET latest → GET project
                                     ↓ согласованная версия и источник
                          чтение операции и SSE / явный повтор POST geometry
```

`usePreparationOperationObservation` читает конкретную квитанцию перед
подпиской, даже если она уже есть в кеше. SSE-ответы проверяются по проекту,
операции, виду и исходной версии. Обрыв показывает последний известный этап и
действие «Обновить статус подготовки», без активного лоадера. Это действие
повторяет чтение, а не подготовку. Корректное событие после восстановления
соединения возвращает наблюдение. Статусы `completed`, `failed`, `cancelled`
и `interrupted` закрывают поток; терминальная ошибка не оставляет анимацию.
После `completed` отдельное чтение проекта подтверждает публикацию и открывает
карту одним запуском подготовки. Ошибка этого чтения оставляет доступным
«Повторить открытие карты» без нового расчёта.

Эти подписки относятся к распознаванию и подготовке проекта в веб-интерфейсе.
Native-передача AutoCAD пока наблюдает квитанцию через отдельный приватный
канал с периодическим GET.

Чтение считается согласованным, когда снимки проекта до и после latest имеют
одинаковые `state_version` и идентичность исходника. Настройки сравниваются
семантически, с независимым от порядка ключом layer/kind/visible. Операция
принадлежит подтверждённой основе, когда совпадают project ID, kind и
`project_state_version`. Завершение дополнительно требует свежей подготовленной
геометрии. Чужая активная операция или изменившаяся пара чтений оставляет запись
заблокированной.

При потерянном ответе PUT API не предоставляет отдельной квитанции этой команды.
Равные настройки на продвинувшейся версии подтверждают только текущее содержимое;
`MappingReceipt.evidence` различает `save_response` и `current_snapshot`.
Неизменная исходная версия не доказывает завершение потерянного PUT: интерфейс
показывает явное сообщение и повторное чтение, а не повторяет запись автоматически.
Гарантия атомарного снимка GET здесь не заявляется; изменение во время чтения
требует повторной проверки. HTTP API и его гарантии If-Match/CAS не менялись.

Recovery VM: `preparationRecovery?: { message, loading, onRetry }`. Пока он есть,
новая подготовка заблокирована. Повтор чтения не запускает новый расчёт. Ошибка
refetch при разрешении конфликта сохраняет исходный конфликт и черновик формы;
сброс выполняется только после успешного свежего запроса.

Проверки: 17 существующих сценариев SetupPage и 10 новых тестов контроллера/
восстановления формы прошли. Проверены потеря ответов save/start, совпадение
основы операции, отсутствие повторного PUT, меняющийся снимок, отказ чтения и
сохранение черновика при failed refetch.

Основания разделения этапов:
[TanStack mutation lifecycle](https://tanstack.com/query/latest/docs/framework/react/guides/mutations)
и [useQuery refetch](https://tanstack.com/query/latest/docs/framework/react/reference/useQuery).

Физическая подготовка сохранённого CAD-захвата — отдельная операция
`prepare_cad_capture`. Основное действие «Подготовить чертёж» выбирает её,
когда нет локального снимка и ещё требуется проверить назначения или границу.
Оно не подтверждает назначения. После завершения обновляется локальная
доступность снимка и продолжается то же действие открытия карты, если текущие
решения допускают расчёт. Непригодная или невыбранная граница оставляет
пользователя на проверке данных. При подтверждённых назначениях и пригодной границе основное действие
«Подготовить карту» сразу запускает `calculate_geometry`: этот сценарий сам
выполняет физическую подготовку и открывает карту после согласованного чтения.
Отдельный запуск `prepare_cad_capture` перед ним не нужен. Решение о пропусках
сохраняется существующей политикой перед расчётом; потерянный ответ этой записи
оставляет доступно только восстановление чтением. Обе операции используют
общий журнал, отмену и политику ухода; неизвестный результат не повторяет POST.
Подтверждённая запись назначений переиспользуется между подготовкой и расчётом,
если её ревизия и значения совпадают; второго сохранения не требуется.
Слои для замыкания могут оставаться неподтверждёнными, хотя очередь ручных ролей
пуста. Если для этого native-маршрута нет локального снимка, основное действие
сначала подготавливает захват и затем продолжает расчёт. `map_ready` у редактора
исходника не подтверждает наличие расчётного снимка.
