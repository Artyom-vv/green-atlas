# Запуск ручного проекта

`useStartWorkspace` соединяет две существующие команды: сохранение участков и
создание ручного плана. Первая запись фиксирует If-Match исходной версии;
подтверждённый ответ становится основой второго POST. Получение готового плана
и публикация в Query отделены от повторения команд.

Попытки, фазы и синхронные gates принадлежат project ID. Переключение A → B не
позволяет позднему ответу A снять gate B. Состояние попытки A продолжает
обновляться, пока контроллер смонтирован, и доступно при возврате в A. Только
владелец видимого проекта получает UI-callback. Карта попыток дополнительно
проверяет идентичность самой попытки перед публикацией и завершением.

Потерянный ответ запуска ведёт к GET проекта. Существующий план принимается без
нового POST. Совпадающие сохранённые участки позволяют явный повтор только
создания плана с версией прочитанного снимка; повторный PUT не нужен. Если GET
не удаётся, writes и reset остаются заблокированы до явного повторного чтения.
Ошибка обновления после подтверждённого плана также требует только чтения.

`api/startWorkspace` проверяет project ID всех трёх ответов. Кэш не откатывается
на более старую версию. Срок жизни команд ограничен смонтированным workspace;
страница блокирует навигацию и сброс, пока команда или восстановление активны.

Проверено 12 случаев: 8 контроллера и 4 API-границы. Среди них A → B → потеря A
→ возврат A, независимые одновременные попытки A/B, чужой project ID,
подтверждённая запись и последующая ошибка обновления. TypeScript и ESLint
проверяют модуль в общей сборке. HTTP-контракты не изменялись.
