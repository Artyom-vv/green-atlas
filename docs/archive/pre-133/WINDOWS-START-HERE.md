содержит полный Windows Setup, SHA256SUMS, отчёт и обезличенную сводку логов.
Тег указывает на точный продуктовый коммит `92fd51b41aa73fff903adbe8bcb602b451946012`,

тестовый нормализатор нового `progress_key` и **не** переименовывает исходник EXE.

В новой версии потоковое чтение подготовленного покрытия ускоряет первый проход;
на ошибке потребителя внутренний SQLite-итератор закрывается немедленно.
Диагностика агрегирует вложенные batch-события. Клиент и API связывают прогресс
по стабильному ключу варианта, устраняя подтверждённый ложный stall при переходе
между горизонтом и базовым годом. На свежей копии Workspace с 77 посадками
непрерывный frozen-прогон дошёл до `resolution` за 62,553 + 4,405 + 12,464 с
(79,422 с); старый контроль 130 занимал 94,680 с за три запроса. Это по одному
прогону с разными версиями диагностики, не строгий многократный бенчмарк.
Apply/Undo/Redo: 77→78→77→78, процесс завершился с кодом 0.

Изолированное обновление 130→131 сохранило 77 посадок, одну зону, байты БД
и истории после обновления и удаления. Отдельная приёмка мастера, всех пяти
picker, настроек и запуска приложения прошла; обе временные Windows-учётные
записи очищены без ошибок. Память дерева Desktop/WebView2/runtime в графической
проверке: RSS 494 022 656 байт в покое и 579 588 096 байт в пике. Память
backend во время расчёта измерялась отдельно; числа и границы замеров приведены
в релизном отчёте. AutoCAD и Blender на этом ПК отсутствуют, а копии жалобы с
99 посадками нет: реальную CAD-загрузку, рендер и все её отмены здесь не доказали.
Подробный [результат M003 в Issue #9](https://github.com/Artyom-vv/green-atlas-dev/issues/9#issuecomment-6278407224).

## M003 — Windows 0.1.131, 20 октября 2026

Исходники M003 продолжают `codex/windows-local-130` в закрытом
`Artyom-vv/green-atlas-dev`. Диагностический журнал из Mac-коммита `54e8478`
пишется только в локальный `Workspace/Logs`; тестовый перенос `05e9307`
исправляет Windows-допущения тестов журнала. Рабочий фикс ускоряет первое
построение паспорта данных: бинарный ресурс теперь передаёт проверенные записи
и WKB одним потоковым проходом, сохраняя SHA-проверки источника и производного
файла, адресные сведения, отмену и время жизни временного движка.

На двух изолированных копиях одного Workspace (77 посадок, одна зона,
18 файлов / 529 980 064 байта, подготовленный JSON есть, бинарного и domain
кешей нет) первый read-only предпросмотр рябины в исходном Python runtime:
77,717 с до фикса (`057d7bf`), 64,504 с после (−17,0%). Пиковая память
дерева backend-процессов: RSS 191 352 832 → 185 266 176 байт; private
538 198 016 → 531 611 648 байт. SHA производного SQLite в обоих прогонах
совпал. Сам поиск одной порции занимал примерно 2,1–2,3 с; миграция JSON в
бинарный ресурс по-прежнему занимает около 34–36 с и этим фиксом не ускорена.
Это время и память исходного backend, не всего приложения с WebView2.

Первый ответ с `time_limit` и нулём принятых посадок — промежуточный прогресс,
а не окончательный отказ. На той же копии после прогрева бинарного ресурса
шесть последовательных запросов в одном процессе обработали
1 536 → 3 584 → 5 888 → 8 192 → 10 240 → 11 543 из 11 543 объектов.
Последний ответ: `resolution`, одна допустимая из трёх запрошенных посадок,
`change_set.can_apply=true`. Данных коллеги с 99 посадками здесь нет; его
точную жалобу это не воспроизводит. AutoCAD и Blender на этом ПК отсутствуют.
Точные build/install receipts новой версии и ссылка на приватный выпуск
публикуются в [Issue #9](https://github.com/Artyom-vv/green-atlas-dev/issues/9).

## Первый этап: настройка на ПК

1. Проверить ОС и архитектуру, свободное место, права текущего пользователя,
   доступ к рабочему репозиторию и Git status. Использовать отдельный checkout.
   Если доступ к GitHub требует входа, дать пользователю выполнить обычную
   авторизацию, не запрашивать пароль или токен в чате.
2. Проверить наличие Git, PowerShell 7, Python x64 3.13.15, Node.js 24 x64,
   7-Zip, MSVC x64 из Visual Studio Build Tools с Windows SDK.
   Версии Python/Node должны соответствовать текущему workflow.
   Настройка сборочной машины подразумевает подготовку недостающих инструментов
   из официальных источников. Системный установщик может потребовать UAC или
   принятия лицензии пользователем; это не ошибка Green Atlas.
3. После клонирования перед каждой командой разработки выполнять из корня
   `. ./scripts/windows-env.ps1` в той же PowerShell-сессии. Все кеши и временные
   файлы держать в `.runtime` этого checkout. Не менять USERPROFILE/HOME.
4. Проверить pinned-версии в `tools/autocad-bridge/windows-ci-inputs.json`,
   `tools/autocad-bridge/windows-product-inputs.json`,
   `tools/autocad-bridge/desktop/build-requirements.txt` и lock-файлах.
   Подготовку Python, uv, pnpm и зависимостей повторять по шагу
   `Prepare locked build dependencies` из
   `.github/workflows/windows-product-build.yml`.
   При локальном повторении заменить служебные GITHUB_WORKSPACE/GITHUB_PATH
   явным путём checkout и PATH только текущей сессии; GITHUB_TOKEN не нужен
   для самой сборки. Не копировать весь workflow как PowerShell-скрипт.
5. Проверить окружение MSVC/Windows SDK. AutoCAD для компиляции не требуется:
   сборка использует ObjectARX SDK 2027. Его официальный URL и SHA уже закреплены
   в windows-product-inputs.json; SDK загружается скриптом, архив EXE не исполняется.
   Согласие владельца на лицензию этого SDK ранее получено. Компиляция не проверяет
   загрузку плагина в настоящем AutoCAD.
6. Создать отдельную рабочую ветку `codex/windows-local-124` от ветки передачи,
   если её ещё нет. Если уже существует, сначала разобраться с её состоянием.
   Не отправлять правки прямо в общую ветку без координации.

Подготовка окружения не требует установки AutoCAD, Blender, Botaniq или PBR.
Подключение реальных библиотек не подменять файлами-заглушками.

## Первые проверки и сборка

До полной сборки выполнить небольшие проверки сценария обслуживания и настроек:

```powershell
. ./scripts/windows-env.ps1
$env:PYTHONPATH = Join-Path (Get-Location) 'apps/api'
& ./apps/api/.venv/Scripts/python.exe -m pytest -o addopts= -q --tb=short scripts/desktop/test_windows_product_install_smoke.py scripts/desktop/test_windows_ci_evidence.py apps/api/tests/test_external_tools_settings.py apps/api/tests/test_blender_runtime.py apps/api/tests/test_native_installation_descriptors.py apps/api/tests/test_desktop_web.py
if ($LASTEXITCODE -ne 0) { throw 'Первичная проверка не прошла' }
```

Полная локальная сборка выполняется существующим скриптом. Перед запуском
убедиться, что OutputDirectory ещё не существует; для следующего прогона выбрать
новое имя, а не удалять предыдущие результаты автоматически.

```powershell
. ./scripts/windows-env.ps1
& ./tools/autocad-bridge/ci-windows-product.ps1 -BuildPython (Join-Path (Get-Location) 'apps/api/.venv/Scripts/python.exe') -OutputDirectory '.runtime/autocad-bridge/local-product-124-01'
```

Скрипт собирает ARX/CRX, native WebView2 host, Web, frozen API и полный Setup.
Он проверяет ISS до длительной компиляции, проверяет SHA входов, создаёт seal
исходников и квитанции. Он не запускает GitHub Actions и не публикует релиз.
На локальном ПК проверить, что отсутствующие CI-переменные не требуются скриптам;
если найдётся зависимость от runner, исправить её явно, сохраняя проверки seal.

## Приёмка интерфейса

Проверять установку в отдельной тестовой Windows-учётной записи без доступа
к рабочим проектам владельца. Запускать сам Setup обычным пользователем.
Создание тестовой учётной записи и machine prerequisite могут требовать прав
администратора: сначала изучить сценарий и согласовать системные действия
с пользователем. Не запускать автоматически весь CI harness на основном профиле.

Сценарии находятся в `scripts/desktop/windows_wizard_smoke.py`,
`scripts/desktop/windows_component_ui_smoke.ps1`,
`tools/autocad-bridge/ci-windows-product-install.ps1`.
Их предпосылки CI-аккаунта и интерактивного рабочего стола нужно проверить
до запуска. Для видимой GUI-проверки Windows должна быть разблокирована.

Обязательные проверки: завершение первого поиска и доступность «Далее», отмена
до установки без записи настроек, установка и запуск по «Готово», пять полей
компонентов, сохранение и повторное открытие, обновление и удаление без изменения
тестовой БД и настроек. Неверный Blender и неполная библиотека должны давать
понятную ошибку. Отсутствие всех компонентов допускает установку приложения.

Важный незакрытый пункт: автоматизация мастера вводит Unicode-пути напрямую,
но не нажимает его кнопки «Обзор». Проверить отдельно accept/cancel всех пяти
кнопок мастера. В настройках приложения предусмотрены accept/cancel пяти picker,
проверка соответствия полям и сохранения прежних значений после отмены; этот
обновлённый сценарий ещё не выполнялся на Windows. Заглушки CAD-папки/.dwt
проверяют только выбор пути и не считаются настоящим AutoCAD.

## Связь с Mac-агентом и результаты

По поручению владельца создан [общий канал Issue 9](https://github.com/Artyom-vv/green-atlas-dev/issues/9)
в закрытом рабочем репозитории. Там размещено задание M001 для уже собранного
локального кандидата. Прочитать актуальное тело Issue и комментарии, отправить
HELLO/ACK с исходным commit и SHA установщика, затем вести результаты там.
Считать Windows подключённой к этому каналу только после её HELLO. Комментарии
Mac/Windows помечаются ролью и номером задания: один GitHub-аккаунт не различает
двух агентов. Задачи не повторять после подтверждённого RESULT без нового номера.

Запуск второго Codex под тем же аккаунтом сам по себе не соединяет агентов.
Сначала проверить доступность Settings > Connections > Control this Mac or PC
и возможность парного подключения с Mac. Сопряжение и вход выполняет владелец.
Не считать канал настроенным, пока Mac действительно не видит Windows-задачу.
Если функции нет, использовать созданный канал Issue 9. Другие каналы и задачи
без поручения владельца не создавать. Комментарий Issue не запускает
простаивающего агента автоматически; чтение выполняется во время активной работы.

Полные логи, оригинальные скриншоты, квитанции и SHA хранить локально в output
или .runtime. В Git отправлять только код, тесты и документацию. Первый итог
дать пользователю в этой Windows-задаче: commit, готовность инструментов,
результат малых проверок/сборки, пути к Setup и квитанциям, доступность Connections,
точное препятствие при его наличии. Короткий итог позволит Mac-агенту продолжить
без пересылки всех логов.

GitHub Actions, платежи, лимиты и тариф не менять. Конкурсный green-atlas
остаётся только для чтения. Непроверенный EXE не публиковать в релизы, включая
черновики. AutoCAD-сценарии и настоящий рендер остаются отдельной приёмкой
на компьютере с совместимым ПО и библиотеками.
