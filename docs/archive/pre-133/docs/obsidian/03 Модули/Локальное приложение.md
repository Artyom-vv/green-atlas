# Локальное приложение

## Подготовка общего runtime к Windows

WebView2 принимает сообщения через собственный message channel в тот же
проверяющий модуль, что WKWebView. Подписка создаётся до ready, снятие канала
отклоняет поздние сообщения. Origin, поколение документа и защита черновика
сохраняются; native host не принимает решение о сохранности формы.

Время жизни API принадлежит одному ExitStack. Он закрывает handoff и локальные
сервисы с БД до освобождения lease, в том числе после ошибки старта или cleanup.
Принудительное завершение ОС проверяется отдельно. Для Core уже написан
Windows Job Object adapter; Windows native host также владеет самим API-процессом.

Форматы AutoCAD installation и Core worker представлены отдельными typed
descriptors. Действующий Mac-поиск сохранён. Windows metadata описывает файлы
и возможности. Windows Core использует собственные процессный и файловый
адаптеры; фактическая приёмка Windows ещё предстоит.
Проверкой SHA и независимых рабочих копий владеет общий `job_files`; сценарии
подготовки и выпуска сохраняют прежний порядок допуска результата.

Native host завершает runtime через `POST /_desktop/shutdown` с пустым JSON
объектом и приватным заголовком текущего запуска. Сессионная cookie Web не
разрешает эту команду. API сначала возвращает `202 {"state":"stopping"}`,
затем закрывает handoff, сервисы, SQLite, lease и listener обычным выходом
сервера. Решение о закрытии документа остаётся у Web; этот маршрут не заменяет
проверку черновика и неизвестного результата записи. Host ждёт завершения всего
своего Job Object до повторного запуска на прежнем порту с новым токеном.

Полная подготовка текущего Mac source включает отдельный preflight поставки
и внешние launch consumers. Эти дополнения проверяются в точном source overlay,
поскольку чистый Git HEAD не содержит весь установленный Mac продукт.
Подключение пользовательской библиотеки растений отложено; основная установка
не требует присутствия Botaniq. Наличие AutoCAD/Blender и квалификация их
исполнения учитываются отдельно.

## Библиотеки дочерних процессов

Собственный упакованный Python worker наследует библиотеки комплекта.
Внешний AutoCAD Core должен использовать системный поиск библиотек. Общая
граница запуска временно меняет DLL-путь только в Windows frozen runtime;
на Mac и в обычном Python она не меняет окружение.

Создание внешнего процесса и собственных workers согласуется одним lock.
После создания восстанавливается фактический DLL-путь API, даже при ошибке.
Ожидание результата, ресурсные лимиты и завершение дерева процессов остаются
у прежнего владельца. Ошибка восстановления после создания процесса также
требует завершить принадлежащий ему процесс, а не потерять ссылку на него.

Граница подключена к Core-запуску и запуску Python workers импорта.
Windows Core supervisor создаёт процесс в собственном Job Object до первой
инструкции, ограничивает вывод и закрывает всё дерево. Файлы имеют отдельный
Windows adapter с native identity и прежними SHA. В точном source
overlay Mac 0.1.119 подключены также Blender, preview-assets и остальные
внешние launch consumers; эти модули передаются отдельно от общего PR.
Смена DLL-пути не означает поддержку всего Windows-приложения.

Приложение можно открыть самостоятельно и вернуться к сохранённым проектам.
Новый CAD-снимок по-прежнему готовит только плагин AutoCAD. Launcher не читает
DWG и не создаёт другое хранилище.

## Установленный вход

На Mac установщик добавляет принадлежащий Green Atlas launcher в
`~/Applications/Green Atlas.app`. Он каждый раз открывает приложение внутри
текущего `GreenAtlasBridge.bundle`, поэтому обновление и восстановление пакета
не оставляют ссылку на предыдущую копию. Runtime, Web и CAD worker остаются
в пакете. Постороннее приложение с тем же именем не перезаписывается.

На Windows конфигурация установленного пакета общая для плагина и запуска
desktop без аргументов. Она проверяет manifest, состав файлов и прямые
относительные пути ресурсов. Workspace и Transfers сохраняют прежние пути.
Установщик создаёт собственный ярлык в Start Menu; обновление и rollback
используют тот же путь. Удаление не затрагивает локальные проекты.

Версия пакета локального приложения отделена от CAD-протокола. На 9 октября
установлен Mac-комплект 0.1.69, CAD-протокол плагина и worker — 0.1.48.
Установленный пакет совпадает с проверенной сборкой рабочей ветки. Launcher
открыл библиотеку с прежними 17 проектами; множественный выбор и снятие выбора
проверены в установленном интерфейсе без удаления пользовательских проектов.
Штатный выход завершил принадлежащий приложению API-процесс; холодный
перезапуск снова открыл библиотеку с теми же 17 проектами. Ярлык рабочего
стола указывает на launcher; предыдущий комплект сохранён для отката.
Windows desktop/package в исходниках
используют 0.1.43 с плагином 0.1.42. Mac packaging сверяет
версию desktop и launcher с собственной версией пакета, а совместимость
проверяет по фактической версии плагина. Windows manifest хранит обе версии,
build_id и SHA файлов, PE resource показывает версию desktop. Обновление
runtime не объявляет новую версию CAD-плагина или новый протокол снимка.

Windows 0.1.43 подготовлен в исходниках. Сборка и приёмка установленного
комплекта на Windows ещё не выполнены; результаты 0.1.42 относятся к прежней
версии.

Первый запуск старого рабочего профиля включает согласованное резервирование
перед миграцией. Mac desktop ожидает готовности до десяти минут; прежний предел
45 секунд мог прервать копирование большой базы. Это время ожидания запуска,
а не таймаут запросов или повтор записей.

## Входящее действие и защита работы

Повторный запуск активирует существующее окно своего профиля. Windows
передаёт только Activate либо идентификатор каталога ticket из 32 hex символов.
Первое окно выводит путь из собственного Transfers; IPC не принимает URL,
произвольный путь, аргументы runtime или локальный session token.

Связь с native-хостом принадлежит окну. Переход между библиотекой и проектом
не пересоздаёт канал и не прерывает локальное чтение. Сессия помощника может
меняться независимо от этой связи.

Обычное открытие не повторяет исторические импорты. Меню передач читает
локальный journal через отдельный authenticated native endpoint. Продолжение
остановленной передачи требует явного действия и `/resume`; saved project
можно открыть отдельно. Получение списка ничего не запускает.

При первом сохранении передачи `/5` индекс экземпляров проверяется вместе
с отображением и перечнем объектов за один проход. Проверки формы массива,
числа экземпляров, уникальности маршрутов, классов и обоих слоёв сохранены.
Семантические сведения проходят отдельную проверку привязки. Формирователь
ticket использует один проверенный SHA отображения в обоих каталогах передачи;
исходный DWG, остальные файлы и локальный приёмник сохраняют свои проверки.
Это устранение повторных проходов, без кеша файлов между действиями пользователя.
Проекция берёт число вершин и габариты из уже проверенных объектов GEOS через
Shapely. Лимиты координат учитывают точки, замыкающие вершины и отверстия;
прежняя геометрия сохранённых проектов остаётся частью общих габаритов.
Подписи записей и всего снимка, точность и допустимость геометрии проверяются
в прежнем порядке.

В рабочей ветке возобновление из меню и кнопки повторения используют один
native-контроллер. До запроса он показывает продолжение передачи и занимает
её идентификатор; новые передачи ждут завершения. Ошибка запроса освобождает
занятое состояние, сохраняя возможность явного повторения. Поздние ответы
после смены runtime, поколения или владельца передачи не применяются.
Регрессионная проверка контроллера прошла. Исправление включено
в установленный комплект 0.1.56. При фактическом GUI-возобновлении Олимпийской
индикация появилась сразу; тот же проект открыт после завершения импорта.

Комплект 0.1.56 собран и установлен с этим контроллером и файловым входом импортера.
Проверены 11 сценариев native-возобновления, подписи и тесты установщика;
375 модулей frozen runtime соответствуют исходникам. Плагин и worker
0.1.47, Web 0.1.55 сохранены точно. Пустой изолированный профиль прошёл
проверки запуска и локальной аутентификации; большой ticket не использовался.
После установки все 269 файлов и символических ссылок совпали со сборкой,
подписи desktop, плагина, worker и launcher действительны. До запуска API
база, WAL и SHM сохранились побайтово; прежние проекты и подготовленный
снимок Кустанайской не изменились. Предыдущий комплект 0.1.55 сохранён.
Фактический GUI-импорт Олимпийской в 0.1.56 завершился: из меню явно продолжен
сохранённый ticket и открыт прежний зарезервированный проект. Повторного захвата
и увеличения лимита не было.

Web владеет решением о несохранённом draft и результате записи. Native
запрашивает уход для меню проектов, нового готового handoff, Close и Quit.
Protocol version 1 связывает решение с documentGeneration и requestId.
Повторный `ready` отменяет ожидающий запрос и повторно сообщает текущую
доступность runtime, сохраняя поколение документа и последовательность запросов.
Оба native адаптера проверяют фактический origin сообщения. Старое решение
не действует на новый документ или новый запрос. Пока bridge недоступен,
загруженная страница не закрывается автоматически. Отмена оставляет работу
на месте; уже сохранённый handoff остаётся доступен в списке проектов.

Неизвестный результат записи при сбое runtime не превращается в разрешение
перезагрузить страницу. Сначала требуется адресное подтверждение результата
через recovery; отсутствие ответа не доказывает отмену записи.

Явный повторный запуск runtime в текущем окне привязывается к прежнему
loopback-порту. Новый дочерний процесс получает новый session token; native
проверяет прежний origin и завершает замену HttpOnly cookie до уведомления
`runtimeRestored`. Документ, draft и documentGeneration сохраняются. Занятый
порт останавливает запуск до открытия Workspace; другой адрес не выбирается.

После обнаружения остановки native отменяет ожидающее решение об уходе.
`runtimeUnavailable` приостанавливает единый API transport и отменяет его
незавершённые запросы. После восстановления разрешено адресное чтение receipt;
потерянный ответ не вызывает повтор записи. Сокет уже начатого соединения
не переключается к новому listener. Между физическим сбоем и уведомлением
процесса остаётся интервал обнаружения; это не гарантия отсутствия запросов
к враждебному локальному процессу в этот интервал.

После разрешения выхода Mac-оболочка посылает SIGTERM своему дочернему API и
подтверждает завершение приложения только после остановки этого процесса.
Ожидание асинхронное и ограничено десятью секундами; при превышении срока окно
остаётся доступным для повторного выхода. Блокировка Workspace не снимается
принудительно, другие процессы не завершаются. Быстрый повторный запуск после
штатного выхода не пересекается с прежним владельцем хранилища.

Текущий stderr находится в `desktop-runtime.log`; перед новым запуском журнал
переносится в `RuntimeLogs`, где сохраняются пять предыдущих журналов. Это
позволяет прочитать первичный отказ после последующего сбоя запуска. Журналы
не содержат закрытую stdout-квитанцию с токеном локального сеанса.

Удаление проекта проверяет его компактную проекцию и ревизию, не декодируя
полный CAD-снимок. Фиксация удаления, отмена активных операций, очистка истории
и индексов используют прежние границы транзакций и проверку `If-Match`.

## Открытие старого проекта

Чтение проекта не переносит расчётный снимок на диске и не создаёт полную
резервную копию Workspace. Снимок версии1 при точном совпадении проверяемого
ключа и известной политики Mac0.1.45 или Windows0.1.42 адаптируется в памяти.
Проверяются хеш содержимого, захват, масштаб и расчётная геометрия.
Кеш использует отпечаток исходного файла; повреждение старого снимка
после первого чтения обнаруживается и при повторном открытии. При явном изменении проверяющего или характеристик сети
совместимый старый снимок сначала сохраняется в новом формате, чтобы изменение
метаданных не потеряло локальную геометрию. Перед таким переносом создаётся
согласованная резервная копия; исходный снимок остаётся на диске. Резервное
копирование также обязательно перед изменением схемы хранения.

В памяти остаётся не больше двух подготовленных проектов: текущий и предыдущий.
Вытеснение кеша не удаляет снимки и не обращается к AutoCAD; повторное открытие
проверяет локальный файл.

Запросы списка проектов и открытия ограничены одной минутой. По истечении срока появляется
ошибка и действие «Повторить чтение»; автоматического повторения нет.
Уход со страницы отменяет незавершённое чтение. Загрузка существующего
проекта не называется созданием нового.

## Отказ передачи и возврат к проектам

Mac-shell различает отказ, прерывание и явную отмену передачи. Экран отказа
показывает точную причину из подтверждённого native receipt, а не заменяет её
общим сообщением о подготовке. Причина отображается обычным выделяемым текстом;
длинное сообщение можно прокрутить. Ответ с ошибкой HTTP сохраняет публичное
сообщение сервиса. Сбой соединения означает неизвестный результат запроса,
поэтому интерфейс предлагает проверить журнал после восстановления связи.

Рядом доступны явный повтор передачи и «К проектам». Кнопка библиотеки и
одноимённое native-меню используют общую проверку несохранённой работы.
После разрешённого ухода shell прекращает наблюдение текущей передачи и
отбрасывает её поздние ответы. Запись журнала не отменяется и не удаляется;
к ней можно вернуться через меню «Передачи AutoCAD…». Причина выбранной
остановленной передачи видна в этом меню до подтверждения продолжения.

Остановка runtime сохраняет последнюю подтверждённую причину передачи.
Если процесс завершился до последнего чтения, после явного запуска runtime
shell один раз читает известный receipt через защищённый native-канал.
Это чтение не отправляет ticket заново, не возобновляет подготовку и не
открывает другой проект автоматически. Новое действие или уход в библиотеку
отменяет прежнее наблюдение. До восстановления runtime библиотека недоступна;
кнопка ошибки запускает сервис, сохраняя загруженный web-документ.

Политика причины и наблюдения проверяется Foundation contract-tests.
AppKit-представление и его вызовы собираются вместе с Mac-shell. Эти изменения
входят в установленный Mac-комплект начиная с 0.1.52. Запуск библиотеки и открытие
сохранённого свежего проекта проверены без открытого AutoCAD. Windows-адаптер этим блоком не меняется.

## Проверки и границы

Общие C++ contract-tests исполняются обоими desktop builders. Mac дополнительно
проверяет Foundation-обёртку маршрутов; installer self-test работает только
в одноразовом каталоге и проверяет launcher ownership, update и отказ на symlink.
Windows resolver/IPC tests запускаются на Windows с окружением из
`scripts/windows-env.ps1`; Mac-сборка не подтверждает работу WebView2,
WM_COPYDATA, Start Menu, Windows DACL или Job Objects.

Native module guardrails для CAD не распространяются автоматически на desktop.
Общие contracts не зависят от AutoCAD, Foundation, WinAPI или сети. Платформенные
адаптеры и установщики остаются отдельными; новая логика не добавляется в main,
если ей нужна самостоятельная проверка.

## Область реальной приёмки

На Mac-комплекте 0.1.55 проверено открытие библиотеки без AutoCAD, в том числе
при запуске через `~/Applications/Green Atlas.app`. Прежняя
рабочая база и проект с 326 посадками сохранены. Обновление установщика не
изменило байты базы; предыдущий комплект сохранён для восстановления.

На свежих захватах плагина 0.1.47 Кустанайской и Олимпийской прошли создание
ticket, его приём локальным сервисом, подготовка сохранённого архива отдельным
Core-заданием, сохранение черновой
посадки, независимое холодное открытие и выпуск CAD-пакета. Координаты, история,
основания и квитанции применения сохранены. Исходные пользовательские файлы
не изменены. Обновлённый Mac UI открыл свежий тестовый проект; установленный
frozen runtime прочитал свежую Олимпийскую и публичную квитанцию записи.

Запуск desktop во время квалификации производителя перехватывался тестовым
инструментом. Приём настоящего ticket установленным runtime проверялся отдельно
через защищённый HTTP-канал; GUI открывал готовый проект. Затем полная цепочка
плагин → native desktop dispatch → новый проект в GUI прошла для Кустанайской
на установленном комплекте 0.1.55 с плагином 0.1.47, без перехвата запуска.
Новый проект сохранён в обычном рабочем профиле; прежний проект с 326 посадками

## Сообщения об отказе фоновой работы

Операция и передача показывают адресное сообщение только для известной
типизированной причины. Внутренняя ошибка получает краткое русское объяснение;
идентификатор операции или передачи связывает его с локальным журналом и стеком.
Текст произвольного исключения не записывается в публичное состояние задачи.
Отмена пользователя и прерывание при завершении приложения сохраняют приоритет
перед поздним сообщением worker. Повтор передачи остаётся явным и использует
прежний идентификатор проекта.

## Владение локальным хранением

Схема десяти таблиц проектов, истории и операций описана SQLAlchemy Core.
Библиотека строит SQLite-запрос и связанные параметры; прежние соединения,
блокировки и транзакции остаются у репозиториев. Сохранение BLOB, проверка
версии и запись квитанции не становятся независимыми транзакциями.

Порядок колонок, типы, nullable, defaults, ключи и частичный индекс операций
сохранены. PRAGMA и имеющиеся три ALTER TABLE остаются явными техническими
шагами; дополнительных таблиц или механизма миграции нет.

Полные `FeatureCollection` полей `geometry` и `source_geometry` сохраняются
репозиторием в неизменяемых gzip-файлах рядом с базой. Запись по одному объекту
и чтение через ijson не создают общую JSON-строку размером с чертёж. SQLite
хранит метаданные, приватные ссылки, SHA-256, размеры и число объектов;
публичный `Project` при полном чтении получает прежнюю геометрию, все атрибуты
и дополнительные поля коллекции. Старые проекты с геометрией внутри JSON
читаются без предварительной миграции.

Файлы публикуются вместе с проверкой CAS. Откат удаляет только собственные
новые файлы, на которые нет сохранённой ссылки; повторная запись одинаковой
геометрии использует существующий файл. История и выпуск проходят через ту же
границу хранения. Выборка отдельных слоёв читает поток одной ревизии, полное
чтение открывает файловые дескрипторы до освобождения SQL-блокировки.
Удаление проекта убирает его неизменяемые файлы, не затрагивая ещё работающий
staging другой операции.

Резервная копия формата `green-atlas.workspace-backup/4` включает все файлы
геометрии, на которые ссылается скопированная база. Отсутствие или нарушение
SHA останавливает публикацию копии и восстановление. Лимит длины записи SQLite
не увеличивается; объекты и атрибуты не отбрасываются.

В комплекте 0.1.83 полный импорт рабочей копии Парковой проверен через HTTP
в отдельном профиле: 539 слоёв, 1170431 объектов исходника, сохранение за 293,9 с.
После перезапуска восстановлены все 1108024 объекта коллекции за 34,1 с;
первый запрос участка карты с построением индекса занял 35,7 с. Весь прогон
занял 365,1 с, максимум памяти дерева процессов — 5,18 ГиБ при лимите 6 ГиБ.
Архив, исходный DWG и атрибуты сохранились. Это проверка импорта, хранения
и повторного чтения; подготовка посадок и выпуск в этот прогон не входили.

В передаче Парковой из GUI 0.1.83 worker был остановлен при превышении лимита
памяти 6 ГиБ. Повтор именно этой передачи в отдельном профиле прошёл за 294,2 с
с пиком 4,80 ГиБ. Файлы передачи и исходный чертёж не изменились; сообщение
о необходимости подготовить снимок заново не соответствовало причине сбоя.

Нормализация 0.1.84 освобождает обработанные исходные записи путей и покрытия
при чтении файла после проверки его SHA. Регионы, точки и предложения
освобождаются после проверки их связей и формирования идентификаторов.
Публичные входы с bytes и dict не меняют переданные данные. Нормализация также
заменяет записи своего списка моделями Pydantic по одной,
освобождая словарные копии до общей проверки снимка. Проверки адресов объектов,
происхождения, полноты ledger, точности и SHA сохранены. Ledger повторно
использует свои индексы; пустой список предложений не строит индексы геометрии.
Превышение памяти имеет отдельную типизированную причину и публичное сообщение
«Не хватило памяти для открытия проекта». Лимит 6 ГиБ и остановка дерева worker
сохранены. Неудачная передача остаётся доступной для явного повтора в прежний
проект; повторная подготовка CAD для этой ошибки не требуется.

Повтор той же GUI-передачи на frozen runtime 0.1.84 занял 287,5 с до сохранения
проекта, вместе с перезапуском и запросом участка карты — 325,9 с. В базе
сохранены 1108024 объекта; карта вернула 29 объектов контрольного участка.
Пик дерева процессов — 5,14 ГиБ при прежнем лимите 6 ГиБ. Прогон прошёл
в отдельном профиле без AI и AutoCAD; файлы передачи и исходный DWG неизменны.
Измерение не показывает существенного уменьшения пика памяти относительно
первого кандидата. Ошибка исходного рабочего запуска зафиксирована журналом,
но в изолированных повторах 0.1.83 и 0.1.84 не повторилась.

Параметры ожидания `5000` мс, журнала `WAL` и синхронизации `NORMAL` принадлежат
проверяемому `shared/storage-config.json`. `configure_sqlite_connection`
применяет их к уже открытому соединению. История использует соединение и
блокировку проекта, без отдельной настройки или фиксации записи.

Активные состояния операции принадлежат `operations/policy.py`. Журнал,
сценарий выполнения и частичный уникальный индекс используют один кортеж
типизированных статусов. Переходы и порядок записи остаются у своих сценариев.

Подготовка карты наблюдается через один поток SSE квитанции операции. Первое
чтение и явное восстановление статуса используют GET; далее журнал уведомляет
поток после подтверждённой транзакции, без периодического чтения базы или CAD.
Переподключение получает текущий снимок, завершённая квитанция закрывает поток.
Отключение страницы освобождает ожидание, сохраняя выполнение самой подготовки

Все производственные изменения прогресса проходят через экземпляр журнала
основного локального API. Его запуск восстанавливает прерванные операции.
Worker импорта подключается с `recover_operations=False`: подключение к той же
базе не вправе прервать живую подготовку другого проекта. Связь UI с квитанцией
проверяет проект, операцию, исходник, вид задачи и исходную версию. Потерянный
ответ команды восстанавливается чтением; повтор подготовки остаётся явным


## Видимое ожидание передачи

В Mac-комплекте 0.1.63 ожидание передачи занимает отдельную
поверхность поверх сохранённого web-документа. Показаны текущий этап журнала,
время текущего ожидания и отмена; библиотека под ним не принимает клики.
Страница и её черновик остаются смонтированными. Ошибка останавливает индикатор
и возвращает доступ к восстановлению и общей политике ухода

Квитанция сообщает `autocad_required`. Для самостоятельного локального захвата
сервис разрешает закрыть AutoCAD после регистрации передачи; старый live-query
остаётся привязан к редактору. Отсутствующее поле означает неизвестность и не
показывает разрешение закрытия. Перед добавлением признака в старый журнал
создаётся согласованная SQLite-резервная копия; идентификаторы и квитанции сохраняются

Mac наблюдает активную передачу одним последовательным GET с ревизией
последней квитанции. Сервер ждёт изменения до 25 секунд и отвечает JSON сразу
после фиксации журнала; неизменённый этап не требует секундного чтения SQLite.
По истечении ожидания возвращается та же квитанция и открывается следующий GET.
Завершённое состояние возвращается сразу. Начальный ответ передачи и явное
восстановление читают текущую квитанцию без ожидания

Ревизия принадлежит одному запуску LocalHandoff и не меняет формат базы.
Отмена HTTP-запроса освобождает ожидающий поток. Разрешённый переход в библиотеку,
выход и смена движка отменяют native-запрос; отказ общей политики ухода оставляет
наблюдение активным. Ответ проверяет поколение, процесс, session token и ticket.
Windows сохраняет прежний транспорт наблюдения до отдельной проверки на Windows

Идентификатор ticket вычисляется штатным SHA-256 до первого запроса. При потере
ответа «Повторить» читает этот receipt, не отправляя новый POST. Если журнал
возвращает `NOT_FOUND`, следующее явное нажатие повторяет тот же ticket;
сервис сохраняет проверку digest и защиту от создания второго проекта.
Неизвестное состояние и чужой receipt
останавливают ожидание. Поздние ответы отбрасываются поколением запроса

### Передача до запуска приложения

Плагин сохраняет панель ожидания на чтении исходника, архивировании подоснов,
проверке замечаний и файлов передачи. Панель скрывается для ответа на замечания
и после отправки запроса на открытие приложения. Готовый ticket означает
завершённую подготовку файлов; принятие передачи подтверждается локальным
журналом Green Atlas. Смена активного чертежа или отмена до отправки прерывает
передачу.

## Чтение проекта и восстановление ответа

Начиная с версии 0.1.68 чтение проекта не обрывается через минуту:
длительность сама по себе не является ошибкой. Отмена наблюдателем, уход
с экрана и остановка локального сервиса по-прежнему освобождают запрос;
поздний ответ отменённого запроса не заменяет проект и его версию.
Долгое чтение предлагает явный повтор или возврат к библиотеке. Повтор сначала
отменяет прежнее чтение, затем отправляет новое; фоновый цикл GET не создаётся.

На текущем backend проверен новый изолированный проект настоящей передачи
плагина 0.1.48: 124 слоя и 99395 объектов. Импорт занял 38,83 с, назначения
и подготовка Core — 88,48 с, из них операция геометрии — 73,57 с. Локальная
посадка и независимое повторное открытие прошли без CAD и AI; план,
координаты, история, основания и квитанция записи совпали. SHA исходного BLOB,
13 файлов передачи и восьми архивных DWG сохранились. Назначения здесь были
техническим предусловием; этот прогон не измеряет точность распознавания.

Версия 0.1.68 была собрана из `84558a4a` и установлена на Mac. Совпадение файлов
установленного комплекта с подготовленным пакетом и подписи проверены;
индекс 17 пользовательских проектов и записи истории после установки не изменились.
Библиотека открылась без AutoCAD, штатный выход завершил локальный runtime.
Зависания чтения и потерянные ответы записи проверены отдельно в UI
на изолированной HTTP-границе; это не проверка нового AI-распознавания или
нового захвата из окна AutoCAD.

Комплект 0.1.69 сохраняет это поведение. В форме подготовки паспорт исходника
читается при раскрытии раздела «Сведения», без предварительной загрузки полного
графа геометрии. Ошибка завершает ожидание внутри раздела; явный повтор читает
сведения заново. Восстановление потерянного ответа сохранения назначений читает
проект один раз и не повторяет запись. Категория защитного футляра описывает
физическое препятствие отдельно от характеристик инженерной сети.
CAD producer и worker остаются 0.1.48; их код и бинарные файлы не менялись.

## Диагностика завершения локального сервиса

В исходниках native-оболочки журнал запуска сохраняет PID оболочки и дочернего
runtime, способ завершения (`exit` или `signal`), код выхода и признаки
закрытия приложения либо таймаута начального запуска. Запись не содержит
токена, адреса сервиса или аргументов процесса. Позднее завершение прежнего
runtime записывается в журнал его запуска, даже после ротации; новый журнал
не изменяется

Диагностика не меняет завершение, повторный запуск или блокировку профиля.
Причина внезапной остановки runtime установленной 0.1.72 пока не установлена:
новые записи доступны после сборки обновлённой оболочки. Сигнал завершения
сам по себе не подтверждает нехватку памяти; для этого нужны системные журналы

## Контрольная точка 0.1.121: история и резервирование

Для подготовленных native-проектов серверная отмена и повтор читают план,
участки и метаданные без построения полного графа координат подложки.
Сохранённые файлы геометрии проходят прежние проверки целостности; ссылки
на них сохраняются. Версия проекта, курсор истории, квитанция и основание
проверки продолжают проверяться при восстановлении. Старые проекты с геометрией
внутри записи и совместимые проверяющие модули сохраняют полное чтение.

Перед изменением схемы создаётся полная точка восстановления. SQLite-снимок
через `VACUUM main INTO` включает зафиксированные записи WAL и исключает
неиспользуемые страницы из копии. Рабочая база не уплотняется. Подготовленные
снимки для исторических планов, связанные CAD-архивы и геометрия сохраняются
с прежними проверками; точка восстановления публикуется после их завершения.

## Подключение AI в выпуске

Mac-комплект может содержать отдельный отзываемый доступ к relay, чтобы AI
работал без ввода ключей. Личный relay и личный OpenAI имеют приоритет над
доступом выпуска. Условия подключения и общий серверный бюджет описаны в
[[Доступ AI в выпуске]].

## Одновременное первое открытие SQLite

Два независимых экземпляра хранилища могут одновременно создавать один
каталог расчётной геометрии. SQLite иногда немедленно отклоняет включение WAL
при такой гонке. Приложение повторяет только этот шаг при `SQLITE_BUSY` или
`SQLITE_LOCKED` в пределах прежних пяти секунд ожидания. После настройки
восстанавливается прежний `busy_timeout`. Другие ошибки передаются вызывающему
коду; соединение и транзакция остаются у репозитория.
