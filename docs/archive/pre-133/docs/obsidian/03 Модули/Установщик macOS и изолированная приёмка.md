# Установщик macOS и изолированная приёмка

Установщик содержит CAD-плагин, фоновый работник, локальное приложение,
замороженный API, Web и ярлык запуска. Пользовательская установка сохраняет
пакет в `~/Library/Application Support/Autodesk/ApplicationAddins`, ярлык в
`~/Applications`, а проекты используют свой прежний каталог Application Support.
Сборка без Developer ID имеет локальную ad-hoc подпись. Она не объявляется
нотарифицированным публичным дистрибутивом.

## Полная воспроизводимая сборка

`build_macos_product.py` требует чистый закреплённый Git checkout и текущий
квалифицированный CPython. Он собирает API, Web, Desktop, GUI-плагин, Core worker
и Installer, затем побайтово проверяет PYZ/bootstrap, все raw-ресурсы и публичные
Web assets. Полный manifest фиксируется после копирования и подписи вложенных
компонентов; исходники проверяются повторно после сборки. Внешние SDK и Autodesk
библиотеки не копируются. Минимальная macOS проверяется по Mach-O runtime;
build target не считается приёмкой на старой ОС.

Уведомления зависимостей и nlohmann MIT сопровождают установщик в
`Contents/Resources/Notices`. Manifest находится рядом, в
`Contents/Resources/distribution-manifest.json`, и описывает вложенный payload.
Эти сборочные сведения не добавляются в устанавливаемый программный bundle:
его строгая проверка удаления сохраняет прежний список разрешённых каталогов.
Для общего физического pnpm store сборщик требует явно указанный корень, точное совпадение
lockfile и наличие каждой фактической пары name/version в закреплённом lockfile.
Лицензия CPython читается из базы именно используемого интерпретатора. Сборочный
отчёт перечисляет отсутствующие тексты отдельно и не объявляет юридическую
проверку лицензий выполненной. Botaniq и PBR остаются внешними ресурсами.

`mac_runtime_qualification.py` запускает именно установленный frozen API с
явными каталогами Workspace, Transfers, Web и worker, очищенным окружением и
собственной группой процессов. Он проверяет приватный доступ, health, пустую
библиотеку, точные HTTP-ресурсы Web и штатное завершение. Снимок рабочих путей
использует хеши установленных компонентов и только файловые метаданные проектов;
рабочие базы не открываются. После приёмки сравнивается тот же набор путей.

## Производственная операция

Установка и обновление сначала копируют и проверяют полный пакет во временном
каталоге назначения. Прежний собственный пакет сохраняется отдельно до замены.
Проверяются идентичность, подписи, frozen runtime и Web, отсутствие QA-профиля
в поставляемом приложении. Посторонние файлы и каталоги через символические
ссылки не заменяются. Пакет и ярлык переключаются одной журналируемой
транзакцией. До commit сбой восстанавливает прежние программы; после успешного
commit удаляются проверенные прежние сборки. Ошибка очистки сохраняется как
ожидающее обслуживание, а не отменяет установленную новую версию.

Обычное удаление из GUI перемещает собственный пакет и ярлык в Корзину.
Проекты и чертежи не входят в эту операцию. Установщик предлагает закрыть
AutoCAD и Green Atlas, а не завершает чужие процессы.

## Изолированная приёмка того же пакета

Явный CLI-режим вызывает производственную `installProduct` и ту же
`GAInstallManagedItems` с отдельными каталогами назначения. Приёмочное удаление
проверяет собственные пакет и ярлык и перемещает их внутри QA-корня. Профиль создаётся только новым, с именем
`GA-Mac-Qualification-UUID`, правами `0700` и текущим владельцем. Его маркер
`.green-atlas-installer-qualification.json` имеет права `0600`, одного владельца,
одну файловую ссылку, schema `green-atlas.macos-installer-qa-root/1`, UID,
`session_uuid`, фазу и совместимое поле `backup`, равное `null` после успешного
обновления. UUID точно совпадает с именем каталога.
Родители и используемые дочерние пути проверяются без перехода по ссылкам.
Отсутствующий leaf не отменяет проверку уже существующих родителей.

```sh
INSTALLER='/absolute/Green Atlas Installer.app/Contents/MacOS/GreenAtlasInstaller'
QA='/absolute/checkout/output/mac-qualification/GA-Mac-Qualification-UPPERCASE-UUID'
"$INSTALLER" --qualification init --root "$QA"
"$INSTALLER" --qualification install --root "$QA"
# Здесь выполняется отдельная приёмка установленного Desktop и frozen API.
"$INSTALLER" --qualification update --root "$QA"
# rollback после успешного commit отказывается: старые сборки уже удалены.
# Восстановление до commit проверяют отдельные транзакционные тесты.
"$INSTALLER" --qualification uninstall --root "$QA"
"$INSTALLER" --qualification purge --root "$QA"
```

Родитель профиля уже должен существовать. Режим не меняет `HOME`, не подменяет
системный Application Support, не открывает приложение через его bundle ID
и не обращается к установленному пользовательскому пакету. Каждый успешный
шаг печатает JSON-квитанцию с фазой и точными путями установленного комплекта.
До обновления и удаления приёмочный запуск обязан завершить свои процессы.

Внутри профиля пакет расположен в `ApplicationAddins/GreenAtlasBridge.bundle`,
ярлык в `Applications/Green Atlas.app`. Отдельный QA-запуск установленного
приложения получает новый `RuntimeProfile`; проверка API использует собственный
профиль. Их квитанции подтверждают запуск отдельно от квитанций установки.
Обычный запуск `.app` продолжает использовать штатный пользовательский профиль.

Production Desktop принимает явные `--qualify-profile` и `--qualify-receipt`
до создания NSApplication. Он требует тот же маркер установленного пакета и
новый `RuntimeProfile`. Настройки восстановления окон меняются только в
volatile-домене памяти процесса; окно не сохраняет своё состояние. WKWebView
использует nonpersistent хранилище. После настоящей загрузки Web проверяются
готовность документа, скомпилированный module script, отрисованная библиотека
проектов, приватный health и пустой список проектов. Затем проверяются HTTP 202
завершения API и код выхода собственного процесса. Приватный токен в квитанцию
не записывается; запуск AutoCAD и рендер этим сценарием не подтверждаются.

После окончания приёмки и подтверждённой остановки собственного API оболочка
возвращает `NSTerminateNow`, сохраняя обычную очистку NSApplication. Повторное
асинхронное ожидание в этой точке создало бы вложенный modal loop внутри main
dispatch handler и заблокировало ответ о выходе в той же очереди. Незавершённая
приёмка, работающий API и отсутствие разрешения на выход сохраняют прежние
проверки; обычный пользовательский запуск не использует эту ветку.

Приёмочное удаление использует общий выбор и проверку собственных файлов,
но удерживает их в `Removed` внутри профиля. Пользовательская Корзина не
изменяется; этот предел явно записан в квитанции. `purge` удаляет только
проверенные собственные пакет и ярлык из `Removed`. После успешного обновления
прежних программных копий нет. Квитанция явно сохраняет
`retained_version_rollback_available=false`, а команда `rollback` отказывается
без изменения фазы или данных.
Маркер, журналы и профили данных остаются для проверки сохранности.
Посторонний или повреждённый объект останавливает очистку.

## Что доказывают проверки

`--self-test` проверяет настоящие установочные функции в отдельном временном
каталоге, включая повреждение бинарного плагина и runtime, отсутствие Desktop,
подмену каталога ссылкой, чужую идентичность, QA-профиль и восстановление после
ошибки ярлыка. Временная повреждённая копия удаляется сразу после своего теста,
чтобы не держать несколько полных frozen payload одновременно.

`qualification-root-tests.mm` отдельно проверяет новый собственный профиль,
права, UID, маркер, UUID, фазу, ссылки и отказ от обычного каталога. Эти проверки
не запускают CAD или API. Сам lifecycle повторно устанавливает тот же payload,
проверяет удаление старых программ, отказ от отдельного отката после commit,
сохранение неизвестного ручного файла и неизменность приёмочных данных после
удаления программ. `test_install_transaction.mm` отдельно проверяет
восстановление до commit при сбое. Это не подтверждает миграцию между разными
версиями; квитанция сохраняет
`different_version_rollback_tested=false` и `product_qualified=false`.

Установка и запуск оболочки не подтверждают чтение DWG, подготовку геометрии,
выпуск CAD или Blender-рендер. Они проверяются отдельно с совместимым ПО и
пользовательскими ресурсами. Общие границы поставки описаны в
[[03 Модули/Подготовка Windows и упаковка|модуле упаковки]], работа приложения —
в [[03 Модули/Локальное приложение|модуле локального приложения]].
