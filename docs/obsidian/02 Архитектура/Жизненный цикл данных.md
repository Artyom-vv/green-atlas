# Жизненный цикл данных

Эта страница объясняет, как приложение освобождает файлы удалённых проектов
и предыдущие установленные сборки, сохраняя возможность продолжить прерванную
операцию. Статус установленного выпуска указан в [[00 Обзор/Текущее состояние]].

## Удаление проекта

Приложение сначала фиксирует удаление проекта и задание очистки в одной
транзакции SQLite. Если транзакция не завершилась, проект и его файлы остаются
доступны. Конфликт версии также сохраняет проект, ручной план и историю отмены.

После фиксации приложение отменяет фоновые операции этого проекта и удаляет
принадлежащие ему файлы. Расчёт или рендер удерживает файловую блокировку до
завершения, поэтому очистка не удаляет файлы из-под работающего процесса.
После освобождения блокировки работник повторяет очистку.

| Данные | Что происходит при удалении |
|---|---|
| Сохранённый проект, исходный снимок в базе, ручной план и история отмены | Удаляются для выбранного проекта |
| Внутренняя копия CAD, геометрия и индекс отображения | Удаляются из управляемых папок этого проекта |
| Расчётные снимки, WKB, контрольные точки поиска, кеши 3D и оформления | Удаляются после освобождения последней зарегистрированной ссылки |
| Задания рендера, подготовленные сцены и файлы передачи CAD | Удаляются по сохранённой привязке к проекту |
| Исходные DWG/DXF и явно сохранённые пользователем резервные копии | Не входят в область очистки |
| Другие рабочие проекты и их ручные данные | Сохраняются |

Привязка файла сохраняется до его создания или повторного использования.
Имена исходных чертежей и пути из CAD не используются как команды удаления.
Для прежних проектов приложение читает небольшие служебные сведения;
неизвестные файлы без доказанного владельца автоматически не удаляются.

Если файл занят, недоступен либо обнаружена подмена пути ссылкой, задание
очистки остаётся в базе. Следующий запуск владельца API повторяет его.
Для внешней папки передачи используется сохранённый управляемый корень,
поэтому изменение настроек не перенаправляет старое удаление в другую папку.

После очистки остаётся небольшая запись об удалённом идентификаторе. Повтор
прежней незавершённой передачи не может заново создать удалённый проект.
Новый импорт получает новый идентификатор.

## Возврат свободного места из SQLite

Удаление строк освобождает страницы внутри SQLite, но само по себе не уменьшает
файл базы. Поэтому та же транзакция удаления оставляет небольшое задание
уплотнения. Его выполняет отдельный фоновый работник владельца API, когда
пользовательские запросы и файловые операции завершены. Дочерние процессы
импорта не запускают ещё одного работника.

Новый HTTP-запрос прерывает уплотнение до своего чтения базы. Работник использует
отдельное соединение и не удерживает блокировку репозитория на время `VACUUM`.
SQLite самостоятельно записывает свою базу и журналы; приложение не заменяет
файл базы и не удаляет WAL вручную.

При занятой базе, открытом читателе, нехватке временного места или закрытии
приложения задание остаётся для повтора. Новый запрос удаления получает
следующее поколение задания и не теряется при завершении прежнего уплотнения.
Мелкие свободные остатки SQLite может использовать для следующих записей.
Полная перепаковка не является обязательной миграцией при каждом запуске.

## Обновление программы

Рабочий профиль с проектами хранится отдельно от исполняемых файлов. Установщик
не запускает очистку проектов и пользовательских резервных копий.
Перед заменой он проверяет комплект и отсутствие работающего приложения или API.

| Граница обновления | Восстановление после сбоя |
|---|---|
| Новый комплект ещё не проверен и не зафиксирован | Предыдущий комплект сохраняется для отката |
| Замена началась, фиксации успеха ещё нет | Следующий запуск установщика восстанавливает прежний комплект |
| Новый комплект проверен, успех устойчиво записан | Новый комплект остаётся текущим, предыдущие исполняемые файлы удаляются |
| Очистке после фиксации мешает занятый файл | Остаётся задание повторной очистки; новый проверенный комплект не откатывается |

На Mac пакет плагина и значок запуска заменяются как одна операция. До
фиксации проверяются приложение, расчётный сервис, загрузчик, CAD-работник
и описание состава пакета. Неизвестные файлы в заменяемом старом комплекте
требуют разбора до замены, чтобы не потерять вручную добавленные данные.

Windows-установщик проверяет полный состав и контрольные суммы пакета,
а также завершение регистрации приложения. Это не заменяет проверку первого
запуска на настоящем Windows-компьютере. После успешного обновления старые
исполняемые сборки не служат постоянным архивом; ручной откат к ним недоступен.
Резервные копии пользовательской базы рассматриваются отдельно.

## Согласованность комплекта

`AppVersion` внешнего `PackageContents.xml`, версии desktop, значка запуска
и установщика Mac должны совпадать. Версии CAD-плагина и CAD-работника
независимы: их допустимость определяется контрактом, а не номером desktop.
Проверка исходных манифестов не заменяет проверку реально установленных файлов,
пути запущенного API, его родительского процесса и выбранного рабочего профиля.

Расчётный снимок SQLite/WKB является ленивым файловым ресурсом. Тесты проверяют
общую границу допуска снимка, целостность исходных байтов и содержимое результата;
сравнение Python-объектов или наблюдение только за прежним JSON-адаптером
не подтверждает этот контракт. Кеш сводки не загружает снимок повторно и не
может скрывать повреждение исходника. Изменение горизонта роста растений само
по себе не меняет полноту CAD-снимка; изменение семантики ограничений требует
повторной проверки основания.

## Отказы выпуска и чтение артефактов

Ожидаемый отказ до публикации CAD-выпуска возвращает `BAD_REQUEST` с конкретной
причиной: например, отсутствует сохранённый архив, недоступен AutoCAD Core,
повреждён работник либо результат не подтвердил исходник и состав посадок.
Проект и прежние выпуски сохраняются; пользователь может явно повторить действие.
Неожиданная ошибка, отмена или потерянный ответ не объявляются успешным выпуском
либо подтверждённым отказом с безопасным автоматическим повтором.

При скачивании опубликованного артефакта сервер сравнивает размер и SHA-256
с сохранёнными метаданными выпуска до передачи вложения. Несовпадение возвращает
`RELEASE_ARTIFACT_CORRUPT`; отсутствующий выпуск, артефакт или BLOB сохраняет
ответ `NOT_FOUND`. Чтение не пересобирает CAD, карту или исторический выпуск.
Позднейшие изменения плана не меняют проверяемые байты прежнего артефакта.
Mac-оболочка отменяет скачивание ответа HTTP с ошибкой до выбора места
сохранения: сообщение сервера не записывается вместо файла выпуска.

## Настройки адресного поиска после установки

Владелец выпуска может явно включить общий ключ DaData в автономный runtime
через `GREEN_ATLAS_BUNDLED_DADATA_SETTINGS`, указав приватный файл с `api_key`.
Сборка переносит только это поле в `Services/dadata.json`; без явного параметра
персональные настройки разработчика не подхватываются. Сам ключ остаётся вне Git
и журналов. Такой ключ извлекается из распространяемого приложения; это временный
согласованный способ поставки, а не защита общего доступа к сервису.

В окне местоположения раздел «Настройки поиска адресов» позволяет сохранить
личный ключ и вернуться к ключу приложения. Приоритет: личный файл, переменная
`DADATA_API_KEY`, встроенный ключ. При отказе личного ключа запрос не повторяется
с общим ключом. Смена настройки сохраняет проект и незавершённое совмещение,
отменяет прежние подсказки и применяет новый доступ к следующим запросам.

Личный ключ хранится атомарно в пользовательской папке `Location/dadata.json`,
вне проекта и установленного пакета. В macOS файл доступен только владельцу.
Локальные маршруты настроек требуют проверенную сессию desktop и возвращают
только источник и наличие доступа. Существующий ключ не передаётся обратно
интерфейсу и не попадает в проект, историю или сохранённый черновик.
Сохранение подтверждает запись настройки; пригодность ключа проверяется
при реальном поиске адреса. Персональные настройки сохраняются при обновлении.
