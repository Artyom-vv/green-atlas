# Подготовка Windows и упаковка

Модуль закрепляет границы, через которые общий код Green Atlas обращается к
установленным программам, файлам поставки и native-оболочке. Он позволяет
готовить Windows-порт без отдельного импортёра, проверяющего алгоритма или базы
проектов. Готовность Windows-дистрибутива пока не подтверждена.

Порядок установки полного кандидата, настройки пользовательских ресурсов и
приёмки: [[05 Эксплуатация/Установка и проверка Windows]].

## Интеграция Mac 130 в Windows

Ветка `codex/windows-mac130-release` объединяет принятый Windows 124
(`845b94a`, документированная вершина `409dcdc`), исправления транзакций
установщика из `18b0948` и сервис Mac 130 (`597a07f`). Базой служит принятый
Windows-порт: его контроль путей и файлов, Win32 Job Object, DLL search,
проверка PE Blender, fsync и закрытие reader до replace сохраняются.
Общие изменения включают расчёт и поиск посадок, освобождение ресурсов проекта,
отказы CAD-выпуска и целостность скачивания, настройки DaData и отдельный relay
доступ выпуска. Новых продуктовых возможностей эта интеграция не добавляет.

Версия продукта и desktop равна `0.1.130`. Исходники Windows ARX/CRX и протокол
не меняются; GUI-производитель остаётся `0.1.48`, Core worker `0.1.49`.
Последний установленный Mac 130 и его проверенный ZIP относятся к `597a07f`;
наличие интеграционной ветки само по себе их не заменяет и не доказывает запуск
Windows 130. Mac-проверки исходников, mock/AST-проверки Windows и реальные
проверки Windows EXE фиксируются раздельно.

Для воспроизводимой Windows-сборки нужны чистый checkout и source seal,
закреплённые SDK/toolchain, полный offline WebView2 и явные два release defaults.
DaData и отдельный revocable relay credential берутся из одобренной поставки
Mac 130, не из профиля разработчика. Значения не включаются в Git, отчёты или
журналы. После freeze и упаковки проверяется их соответствие входным файлам;
платный запрос к AI не нужен для проверки состава. Работа AI и адресных подсказок
на другом ПК требует интернета; лимит relay не увеличивается при установке.

Повторное использование ARX/CRX 124 требует собственных исходных build receipts,
source inventories и совпадения байтов с принятым комплектом. Ранний локальный
бинарник с тем же номером версии не заменяет эту проверку. При отсутствии
исходных receipts нужна сборка неизменённых native-исходников и отдельная
квалификация. Нельзя выпускать EXE без frozen API, актуального Web и проверки
версий лишь потому, что старый установщик запускался.

Ресурсы Botaniq и PBR остаются внешними: получатель распаковывает приватный
комплект и выбирает папки и Blender через существующий мастер. Для готового
прототипа сохраняются ручные посадки, зоны, история, CAD-архив и авторитетные
снимки; переносимые файлы проверяются по SHA. WKB/RTree и кеши отображения
восстанавливаются локально. Подготовленный проект позволяет проверить сервис
без нового импорта; для захвата и CAD-выпуска нужен установленный AutoCAD 2027.

До передачи нового Windows EXE обязательны: чистая установка обычным
пользователем без devtools, обновление 124 с непустым проектом, сохранность
посадок/Undo/Redo после перезапуска, реальные файловые блокировки и восстановление
после прерванного обновления, очистка старых программных сборок без удаления
Workspace, затем GAOPEN/подготовка/выпуск в AutoCAD и рендер с реальными ресурсами.
Эти проверки выполняются на точном собранном EXE с сохранением SHA и квитанций.

## Нативный мастер Windows

Локальное изменение жизненного цикла установщика от 19 октября сохраняет
прежнюю сборку только до подтверждения обновления. Подтверждение означает
полную проверку состава и SHA программного комплекта и успешную публикацию
ярлыка и записи удаления. Это не проверка первого запуска API или AutoCAD.
До подтверждения журнал восстанавливает прежний комплект при следующем
запуске установщика. После подтверждения старые проверенные программные
комплекты удаляются; ошибка удаления оставляет новый комплект текущим и
сохраняет журнал для повторной очистки. Частичное удаление продолжает работу
по сохранённому перечню файлов, без требования целостности уже удалённой копии.
Журнал хранит не более одного перечня удаляемого комплекта одновременно.

Ссылки, reparse points, чужие файлы и неполные прежние установки не удаляются
автоматически. Неполная распознанная установка сохраняется адресно, поскольку
в ней могут оказаться неизвестные пользовательские данные. Workspace,
Transfers, исходники CAD, ручные архивы и резервные копии миграции БД не
относятся к программным копиям. В Installer/Versions после успеха очищаются
проверенные старые Setup; текущий обслуживающий и реально исполняемый EXE
сохраняются. Ярлык «предыдущая версия» больше не создаётся. `--rollback` после
успешного обновления объясняет, что исторический пакет не сохранён; явный
выбор проверенной копии, оставшейся от прежнего установщика, поддерживается.

Проверки исходников на Mac завершают отдельный процесс установщика на границах
копирования, переключения, публикации оболочки и очистки. Они проверяют
возврат прежней версии до подтверждения и сохранение новой после подтверждения.
Новая сборка EXE и проверка этого изменения на Windows ещё не выполнялись:
ПК выключен. Ранее опубликованные установщики этим изменением не обновлены.

Версия Windows-приложения берётся из общего `PackageContents.xml` и сверяется
с версией desktop. Сборщик переносит её в Windows-регистрацию, host, имя EXE
и квитанции backend/мастера. Версии GUI-производителя и Core при этом не меняются:
они принадлежат своим metadata. Расхождение версии host и продукта останавливает
упаковку. Проверка Windows CI исполняет и PowerShell-границу чтения версии.

Контрольная точка 0.1.121 объединяет Windows-адаптеры с бинарным расчётным
хранилищем, постоянным индексом отображения и компактной историей плана.
Отдельная группа Windows CI исполняет тесты этих хранилищ, посадок, истории
и viewport на настоящей Windows. Успешные тесты исходников отдельно от сборки
frozen API и установки не означают приёмку AutoCAD или Blender.
Производные SQLite-файлы синхронизируются через дескриптор с правом записи
до публикации. При восстановлении повреждённого расчётного производного файла
проверяющий reader закрывается до атомарной замены; исходный SHA-снимок
по-прежнему остаётся основанием восстановления.
Дополнительный HTTP-сценарий создаёт собственный синтетический подготовленный
проект и исполняется отдельно для исходников и перенесённого frozen EXE с чистым
PATH. Он проверяет закрытый доступ, проверку точки, автопосадку, применение,
Undo/Redo, штатное завершение, повторное открытие и сохранность SHA-снимка.
Данные пользователя и установленный AutoCAD в этом сценарии не используются.
Расширенный runtime job имеет общий бюджет 35 минут. Короткая проверка Python и
самого владельца процессов исполняется напрямую до использования этой обвязки;
его Windows-тесты сохраняют ограничение pytest. Остальные Python-фазы запускаются
в собственном Windows Job Object с отдельным сроком ожидания и журналом; оставшиеся
потомки закрываются до следующей фазы. Лимиты pytest-сценариев сохраняются.
Длительная компиляция production frozen API в GitHub Actions проходит через
ту же границу с отдельным сроком 1200 секунд и потоковым выводом. При отказе
сохраняется журнал компилятора; путь готового EXE остаётся единственным результатом
PowerShell builder для вызывающего сценария.
Ручной режим `windows-build.yml` с `runtime_scope=optimized` завершает отдельную
проверку исходников после общего набора storage/geometry и HTTP-жизненного цикла.
Он запускает pytest напрямую из PowerShell, без компилятора и его обвязки,
не проверяет её собственные тесты, версию установщика и host. Для этого режима
заданы 8 минут на шаг, 15 минут на job и 45 секунд на testcase; квитанция содержит фактический Git
commit, число пройденных testcase без пропусков и явную границу source-only.
Режим `full` и обычный push сохраняют все проверки обвязки и runtime.
Результаты этих двух режимов не подменяют друг друга.
Source-only workflow распределяет тот же список 24 модулей и HTTP-сценария
между четырьмя отдельными Windows job, не более двух одновременно. Каждая
проверка принадлежит ровно одной группе. Ошибка группы не отменяет остальные;
для общей приёмки нужны успешные результаты всех четырёх на одном commit и
суммарно все 853 testcase без ошибок и пропусков. Квитанция `/2` указывает номер
группы, выбранные входы и то, что одна группа не исполняет полный набор.
Ручной `SourceShard=0` и полный режим сохраняют единый полный список.
Диагностический режим `focused` исполняет шесть модулей первой группы по
отдельности: группы 2–4 на Windows уже прошли 754 testcase, первая ещё не дала
результат. `SourceCheckIndex` записывается в квитанцию; отдельный модуль не
квалифицирует общий набор. Этот режим имеет собственную concurrency-группу и
не отменяет продолжающуюся общую проверку.
`storage-trace` оставляет те же 19 тестов хранения исходников и резервных копий,
но отключает общий перехват вывода, отмечает начало/конец testcase через штатные
Actions notice и включает дамп faulthandler через 25 секунд. Предел testcase
45 секунд и исходы pytest сохраняются. Это дополнительная диагностика без
квалификации полного набора; текущие optimized и focused job не отменяются.
В параметризации хранения исходника вариант с данными размером 1 МиБ + 7 байт
получал nodeid длиной 1 048 673 символа. pytest сохраняет nodeid и фазу в
`PYTEST_CURRENT_TEST`; Win32 ограничивает значение переменной 32 767 символами.
Вариантам даны короткие `ids`: сами данные, количество случаев и проверки
целостности сохранены. Повторная Windows-проверка должна подтвердить, устраняет
ли этот дефект остановку группы хранения и общего runtime.
Аудит коллекции всех 5074 API-testcase выявил ещё один такой случай: параметр
проверки настроек рендера создавал nodeid на 65 630 символов. Он также получил
короткий `id`, при сохранении 65 537 символов во входном файле и прежнего отказа
на повреждённых настройках.
Полный runtime включает и 23 проверки настроек внешних ресурсов: повреждённый
JSON, лишние и повторные поля, предел размера и запрет скрытого fallback.
`windows-complete-suites.yml` дополнительно проверяет всю API-suite четырьмя
непересекающимися группами модулей, полный Web и API client на Windows. Это
расширенный аудит платформенной совместимости; причины platform-specific skip
сохраняются в отчёте. Обязательный набор 853 testcase без пропусков и отдельная
приёмка frozen API сохраняются. В artifacts попадают только выбранные имена
модулей и JUnit, без временных баз, CAD и тестовых профилей.
При проверке rollback неизменность чужой dangling-ссылки сравнивается с её
исходным `readlink()`: Windows может вернуть цель с префиксом `\\?\`.
Отдельный `windows-pattern-diagnostic.yml` выгружает только собственный
синтетический payload «контур здания» для сравнения платформенных результатов.
Транспорт ограничен 256 КиБ и SHA256; эталон координат этим workflow не меняется.
Проверки паспорта наблюдают общую границу загрузки снимка для WKB и старого JSON,
сохраняя запрет лишней гидрации, ограничения памяти и проверки целостности.
В fixtures локальной правки данные ленивого снимка фиксируются до удаления
исходных файлов; сравнение физического основания использует полные данные,
а не идентичность двух объектов-обёрток. Производственные проверки не ослаблены.
Source-only запускает Python штатной командой PowerShell с выводом прямо в
журнал Actions. Он не использует диагностический Python-драйвер, файловое
перенаправление или .NET Process: это независимый контроль исходников при
неподтверждённой работе этих механизмов. Лимит шага оставляет время на сохранение
JUnit и завершение job, чтобы не терять журнал из-за общего timeout.
Bootstrap полного режима использует встроенный Python faulthandler:
через 120 секунд незавершённая фаза печатает стеки и завершается с ошибкой. Собственный дубликат stderr сохраняет дамп вне fd capture pytest.
Таймер остаётся активным при завершении интерпретатора, чтобы выявлять оставшиеся
потоки. Python сам направляет нативные stdout/stderr в новый файл, исключая
зависимость диагностики от каналов PowerShell. После выхода PowerShell печатает
конец журнала, сохраняя фактический код возврата. Это драйвер CI, не граница запуска
AutoCAD или Blender в продукте.
PowerShell запускает bootstrap полного режима через `ProcessStartInfo.ArgumentList`
с внешним `WaitForExit`. Через 15 секунд после внутреннего срока он останавливает
только своё дерево процессов и возвращает 124. Ожидание не зависит от обработки
нативных потоков PowerShell; данные и процессы текущей установки не затрагиваются.
Для запуска без окна stdout и stderr явно перенаправляются в каналы .NET и
читаются одновременно. Это даёт Python действительные handles до открытия
файлового журнала и сохраняет ошибки раннего запуска. Неявное наследование
вывода на Windows runner привело к `OSError(9, 'The handle is invalid')` ещё
до первой проверки Python; такой прогон не подтверждает работу исходников.

Длинные пользовательские пути переносятся по ширине страницы. Итоговая сводка
использует только вертикальную прокрутку, чтобы пути и пояснение WebView2 читались
без горизонтального прокручивания. Страница папок использует native Memo только
для чтения: полный путь можно выделить и скопировать; длинная непрерывная строка
не обрезается статической меткой.

Пользователь запускает внешний мастер Inno Setup, ревизия установщика 2.
Его первое окно появляется до распаковки большого frozen backend. Последовательность:
приветствие, папки программы и проектов, выбор ярлыка рабочего стола,
подтверждение, видимые этапы установки, завершение с запуском Green Atlas.
Папка программы фиксирована для регистрации плагина AutoCAD и явно показана;
проекты хранятся отдельно. AutoCAD и Blender не блокируют установку оболочки.

`wizard.iss` владеет нативными окнами, выбором ярлыка и переходами. Он запускает
проверенный по SHA backend из `setup_entry.py`. Backend продолжает владеть
mutex, проверкой закрытых приложений, preflight, установкой Microsoft WebView2
и транзакцией `BundleInstaller`; frontend не копирует bundle самостоятельно.
На странице компонентов мастер принудительно рисует подписи, поля и состояние
поиска до синхронного ожидания backend. Иначе первый кадр страницы оставался
частично пустым до завершения поиска.
Поток фиксированных `GA_STAGE` сообщает реальные этапы, без выдуманных процентов.
До операции проверяется закрытие приложений; в критической секции кнопка отмены
недоступна. Старая quiet CLI сохранена для проверок и восстановления.

Если прежний Windows Setup оставил `GreenAtlas.bundle` с регистрацией Green Atlas
и ARX, но без `distribution-manifest.json`, новый backend распознаёт эту
неполную установку и атомарно переносит её в соседний
`GreenAtlas.incomplete-<id>`. Он не удаляет файлы внутри и не включает такой
каталог в автоматическую очистку backups. Новый проверенный bundle занимает
обычный путь; при отказе публикации прежняя папка возвращается на место.
Неизвестный каталог или комплект с повреждённым существующим манифестом
по-прежнему блокирует замену. CI проверяет этот случай на настоящем Setup
в отдельном профиле, дополнительно к малым тестам транзакции.

Во время запуска Windows host показывает нативное светлое ожидание и держит
WebView2 скрытым до успешной загрузки локального документа. Меню подготовки
в AutoCAD использует масштабируемый Segoe UI. При передаче модуль сравнивается
с ARX из установленного комплекта по идентичности файла или SHA-256 копии,
поэтому регистр символов и алиас пути AutoCAD не вызывают ложный отказ.
Приложение запускается только из установленного комплекта. Если AutoCAD
загрузил другой ARX, сообщение показывает фактический путь; отсутствие
компонента, неверная конфигурация и код Windows сообщаются отдельно.
Сформированные файлы передачи
остаются в локальном списке для повтора. Визуальный результат в AutoCAD 2027
требует проверки на машине с установленным редактором.

В HKCU остаётся одна запись Green Atlas. `NativeUninstaller` указывает только
на обычный EXE из собственного `GreenAtlas/Installer/Wizard`, `BackendSetup` —
на сохранённый backend с именем каталога по его SHA. Удаление через Windows
использует native uninstaller и тот же backend, сохраняет Workspace и удаляет
только проверенные программные резервные копии. Вызов старого обслуживания
сохраняет подключённый native-вход, если он уже зарегистрирован.

Компилятор Inno Setup закреплён по версии, SHA и подписи издателя; конечному
пользователю он не нужен. `windows_wizard_smoke.py` предназначен для нового
обычного CI аккаунта: реальные окна и GDI-кадры, отмена до установки, правильные
пути и ярлыки, запуск по «Готово», обновление и native-удаление с сохранением БД.
Проверка backend отдельно не подменяет эту проверку UI. AutoCAD и Blender
этими сценариями не квалифицируются.

Локальная Windows-приёмка M001 от 18 октября 2026 года прошла под отдельным
обычным SID без AutoCAD и Blender: native Setup, запуск Desktop/API/WebView2,
пять picker в настройках, отказ неверного Blender, сохранение настроек,
повторная установка, удаление и пять кнопок Browse мастера с выбором и отменой.
Для проверки неверной версии Blender сценарий использует копию штатного
`where.exe`. Отдельная проверка в frozen backend отклонила повреждённый
`blender.exe` до запуска через `GetBinaryTypeW`: код 2 и сообщение о требовании
64-разрядного EXE без системного диалога Windows. Два теста защиты от symlink
прошли в разрешённом повышенном процессе. Кадр первого появления страницы
компонентов показывает полную разметку во время поиска. Дочерняя и
верхняя квитанции имеют `passed=true`, очистка
временного SID прошла без ошибок; 37 кадров и квитанции лежат только в локальном
`.runtime`. Полный backend и мастер собраны из одного source manifest
`c4a2a0d3b99f4fe2a5dddd769e5dd6ce8ca50c0051d027e4ae78ba59eebb3ce5`.
Проверенный локальный Setup 0.1.124 имеет SHA-256
`39d5c4388b4a27ef06bb092d59aa8342c33f1cf17d48ad64207a5bf3321c5c51`.
Это ещё не опубликованный релиз; `product_qualified=false` до приёмки AutoCAD
и Blender на оборудованной машине.

Отдельный CI-сценарий обновления получает опубликованный установщик 0.1.119
из рабочего репозитория и сверяет закреплённый SHA. В новой обычной учётной
записи прежний EXE создаёт проект, новый мастер обновляет программу, новый
EXE открывает прежний проект, затем native uninstaller удаляет программу.
До первого запуска новой версии и после удаления сверяются байты рабочей БД.
Контроль относится к сохранённому проекту без CAD-основания; миграция реального
подготовленного CAD-проекта требует отдельной приёмки.
Сценарий обновления, как и UI-проверка, устанавливает полученное через token
окружение текущего SID до обращения к known folders: иначе Shell может развернуть
путь через унаследованный профиль административного CI launcher.
При отказе install harness выводит в журнал CI ограниченную сводку ошибки
собственного тестового профиля. Это сохраняет диагностику при недоступной
выгрузке artifacts; окружение процесса в сводку не входит.
Отдельный транспорт сохраняет в журнале ограниченные квитанции и исходные PNG
собственного UI-прогона с SHA и размерами. Он читает только фиксированный CI output,
не экспортирует окружение, не меняет изображения и не переносит EXE через журнал.

UI-проверка получает полное системное окружение собственного обычного SID через
`CreateEnvironmentBlock`, затем задаёт только checkout Temp. Это сохраняет
системные пути WebView2. Перед кадром приложения проверка ждёт готовности его API
и приватной WebView2-сессии, а не только появления пустого окна.

В `Contents/Windows/Notices/Dependencies` сборщик сохраняет тексты уведомлений
и точные metadata установленного Python-окружения сборки и локального pnpm store.
Отдельно включается текст лицензии поставляемого CPython из его базового каталога;
Windows-сборка прекращается, если этот текст не найден. Он не импортирует код пакетов и не обращается к сети. Отсутствующий текст лицензии
отмечается в `third-party-notices.json` вместе с исходными полями metadata;
это не является лицензионным допуском. Модели Botaniq, пользовательские ключи
и рабочие данные этим сборщиком не копируются.

## Основание и версии

Полное основание подготовки — принятый снимок исходников Mac 0.1.119 и явно
перечисленные изменения поверх него. В этом снимке GUI-производитель захвата
имеет версию 0.1.48, Core worker — 0.1.49. Версии desktop, API/Web-сборки,
производителя и работника сохраняются независимо. Совместимость определяется
разрешённой парой и протоколами, а не равенством всех номеров.

Windows-ветка включает актуальный продукт из `codex/stable-local-project`:
рендер, местоположение, единый сценарий роста, Web и API-клиент находятся вместе
с платформенными адаптерами. Для следующей сборки используется один Git checkout.
Предыдущие FULL119 архивы сохраняют свои исходные manifest и квитанции.
Набор исходников, установленный Mac-пакет и запущенный API имеют отдельные
квитанции; один не подтверждает другие.

## Вход, обработка и результат

| Часть | Вход | Результат и ответственность |
|---|---|---|
| `AutoCADInstallation` | Выбранная платформа и путь либо обнаружение установки | Пути Core/DWT и идентичность AutoCAD 2027; только описание установки |
| `WorkerLayout` | Каталог поставленного работника | Файл, метаданные, независимая версия, SHA и объявленные возможности |
| `job_files` | Проверенный CAD-комплект и каталог отдельного задания | Проверка файлов, независимые копии и допуск Mac-работника; исходник не меняется |
| `child_dll_search` | Создание собственного Python worker либо внешней программы | Раздельный поиск DLL на Windows; ожидание процесса происходит после восстановления поиска |
| `BlenderInstallation` | Явный путь или обычный поиск Blender | Описание executable; отдельный `probe_blender` читает только `--version` |
| `distribution` | Каталог собственного payload, layout и source seal | Manifest и проверка размеров, SHA, относительных путей и компонентов |
| `desktopBridge` | Сообщение WKWebView либо WebView2 | Общий parser, origin, поколение документа и идентификатор запроса |
| `local_platform` и Windows GUI adapters | Открытый документ AutoCAD | Прогресс, отмена, XREF, закрытые очереди и текущая передача `/5` |
| Windows WebView2 host | Фиксированные launch metadata и ticket ID | Собственный API job, cookie, native handoff, leave/restart и сохранение загрузок |
| Windows installer engine | Проверенный manifest собственного bundle | Staging, переключение, rollback, удаление регистрации и сохранение рабочих данных |

`job_files` выделяет общую файловую ответственность подготовки, native query и
CAD-выпуска. Действующие проверки SHA, независимости копий, размеров и итоговых
квитанций сохраняются. Посадки используют один подготовленный локальный снимок;
выделение адаптеров не запускает AutoCAD для каждой посадки и не создаёт второй
CAD-вход.

На Windows путь к будущему каталогу CAD-архива или геометрии проверяется по
существующим компонентам через Win32 handles. Отсутствующая часть пути допускается
до атомарного создания; существующие reparse points, неоднозначные имена и
неожиданные файлы вместо каталогов отклоняются. Чтение уже опубликованного файла
по-прежнему требует отдельного открытия и проверки его handle. Кеш допущенного
CAD-архива сверяет полный Windows File ID и ChangeTime: возврат прежних размера и
времени записи не делает изменённый файл прежним.
Тот же отпечаток используется для подготовленной геометрии и кеша покрытия:
потоковый reader конверта и бинарное SQLite-хранилище передают один формат
Win32-отпечатка в `PreparedStore.accept_verified`.
Он берётся из Win32-метаданных как по пути, так и по открытому файлу, поскольку
Windows `stat` и `fstat` дают несовпадающие `st_ctime_ns` даже без изменения файла.
Горизонт просмотра не меняет CAD-основание или сводку покрытия; тесты сохраняют
кеш при его изменении согласно `preparation_basis`.
При первом создании проекта каталог блокировок ресурсов на Windows создаётся через
Win32-проверку всей цепочки без reparse points, затем открывается обычный lease.
Назначенный извне каталог Transfers может ещё не существовать: проверяется его
имеющийся префикс. Очистка после удаления проекта пропускает отсутствующие
производные каталоги, но проверяет каждый существующий каталог до обхода.
При записи резервной копии файла используется дескриптор с правом записи:
Windows требует его для `fsync`, поэтому сохранение и восстановление проекта
проходят тем же путём, что и на macOS.
JSON-квитанции рендера и кеш OSM читаются и записываются явно в UTF-8, чтобы
кириллица не зависела от системной кодировки Windows.

Граница DLL используется при создании внешних Blender/Core-процессов и
разрешённых собственных Python workers. Она не владеет ожиданием, отменой или
публикацией результата. На Mac сохраняется прежнее окружение; Windows-задание
Blender дополнительно получает собственные `TEMP` и `TMP`.

`probe_blender` распознаёт отдельную строку версии и сохраняет полный вывод:
предупреждение нативной библиотеки перед этой строкой не делает установку
неизвестной. Произвольное упоминание Blender внутри сообщения версией не считается.
Отдельный ручной CI `windows-blender-check.yml` получает официальный portable
Blender 4.5.11 по закреплённому SHA. Он создаёт собственную модель и текстуры,
исполняет production workers PNG и GLB, проверяет неизменность проекта и
исходных ресурсов, затем повторное использование кеша. Эта проверка не использует
Botaniq и не подтверждает внешний пак, AutoCAD или запуск из frozen API.

Временный каталог конвертера GLB имеет короткое случайное имя без повторения
64-символьного ключа кеша. Это сокращает путь записи Blender на Windows:
проверка с настоящим worker выявила отказ при пути в 276 символов.
Итоговый адрес кеша, идентификаторы ресурсов и проверка manifest/SHA сохраняются.
Повторный Windows-прогон `39081874285` на исходниках `307b28a` подтвердил PNG,
две GLB-модели, девять текстур, повторное использование кеша и неизменность
исходников/проекта. Загрузка артефактов этого прогона отказала из-за квоты GitHub;
успешный worker и его квитанция доступны в журнале задания.

Desktop runtime регистрирует закрытие принадлежащих ему handoff, сервисов и
соединений до освобождения профиля. Ошибка запуска проходит через ту же границу
очистки. Web владеет решением об уходе и сохранностью формы; native host только
передаёт намерение. Listener WebView2 и прежний callback WKWebView используют
одни проверки и снимаются при закрытии документа.

## Проверка поставки

`build_manifest` сверяет файлы source seal и 14 необходимых JSON/raw helpers в
frozen runtime, затем фиксирует весь собственный payload. `check_package` читает
готовый manifest без source checkout и проверяет отсутствие изменений. По
умолчанию результат имеет статус `draft`, квалификация не заявляется.

Внутренние относительные ссылки PyInstaller runtime допустимы, если цель остаётся
в том же runtime. Абсолютные, повреждённые и выходящие наружу ссылки, чужие
reparse points, developer-каталоги и рабочие CAD/базы отвергаются. Версия
Core worker проверяется вместе с его идентичностью. Для текущей сборки 0.1.49
требуются объявленные протоколы `/1`, `/2`, `/3` и формы `curve`, `AcDbRegion`,
`AcDbHatch`. Метаданные ещё не подтверждают реальную загрузку CRX в AutoCAD.

Проверка Web подтверждает только локальные ресурсы документа и отсутствие
известных developer origins. Сборщик обязан задать `VITE_API_URL=''` и отдельно
проверить фактическую работу compiled Web на приватном origin API. Source seal
и raw helpers не доказывают соответствие Python-кода внутри PYZ. Для
квалификации требуются отдельно полученные сведения о compiled API и реальных
сценариях; совпадение квитанции проверяется по source и всем компонентам.

Mac-упаковка при заданном source seal создаёт manifest окончательного вложенного
payload после копирования и переподписи GUI, до подписи внешнего installer.
Ошибка проверки останавливает упаковку. Прежняя локальная сборка без seal не
получает утверждение о квалификации.

## Зависимости и отложенная библиотека

Каталог правил, виды, сообщения, Web и Python-зависимости принадлежат собственной
поставке. SDK, интерпретатор разработки и Node нужны сборщику, а не конечному
пользователю. AutoCAD и Blender описываются отдельно: `installed_not_probed`
означает найденные файлы, а не успешную подготовку или рендер.

Ресурсы растений имеют отдельный статус `user_supplied`. Их отсутствие не делает
core payload повреждённым. Новый интерфейс библиотеки, кнопка подключения и
автоматическая инициализация каталога ресурсов отложены. Текущие настройки и
принятые ресурсы не заменяются; готовый каталог на чистом профиле этим участком
не обещается.

## Реализованный Windows-кандидат

GUI ARX использует текущий общий захват, archive, inventory, instance mapping
и semantics. `local_platform` изолирует процессы, каталоги, ACL и файлы очередей.
Четыре Windows адаптера владеют интерфейсом подготовки, поиском XREF, записью
билета и запуском фиксированного установленного host. Передача `/5` с
native-session `/3` не заменена прежним Windows `/4`. Внутренние протоколы
остаются UTF-8; файловая система Windows получает UTF-16 через
`filesystem_utf8.h`. Полные Mac GUI и Core собираются с этими общими изменениями.

Windows `PackageContents.xml` явно загружает GUI ARX при старте AutoCAD:
регистрация native-меню и контекстного пункта выполняется в инициализации
модуля. Одна загрузка по `GAOPEN` оставляла бы оба пункта недоступными до
ручного ввода команды. Команда `GAOPEN` также остаётся зарегистрированной
для вызова; сама подготовка начинается только по действию пользователя.
Синтаксис параметров загрузки сверяется с
[описанием Autodesk](https://help.autodesk.com/cloudhelp/2027/ENU/AutoCAD-Customization/files/GUID-3C25E517-8660-4BB7-9447-2310462EF06F.htm).
Это исправляет состав регистрации; фактическое появление меню и загрузка ARX
на Windows входят в отдельную физическую приёмку.

Окно хода `GAOPEN` отрисовывается отдельным Win32 UI-потоком с Segoe UI,
подписями текущей фазы, количеством объектов и анимированной полосой.
Всю клиентскую область можно перетаскивать, пока поток AutoCAD занят захватом.
Локальный MSVC smoke-прогон подтверждает компиляцию и показ окна, но сборка
ARX с ObjectARX SDK и внешний тест в AutoCAD остаются обязательными.

Windows host использует WebView2 с локальным Web и приватной cookie. Только
native HTTP-запросы получают заголовок токена. Входной IPC принимает 32 hex
символа ID билета из фиксированного Transfers, без пути, URL или токена.
Готовность API, origin, поколение документа и request ID проверяются отдельно.
Решение об уходе принадлежит Web, включая черновик и неизвестную запись.
Остановка API использует native-only shutdown, ожидание всего job и новый токен
при перезапуске на прежнем порту. Подготовка и выпуск продолжают проверять SHA,
worker capabilities, завершение дерева и lifecycle receipt.

Native build recipe содержит Core и GUI source closure. PowerShell parser
проверяет AST без исполнения скриптов. SDK, MSVC, Win32 API, загрузка ARX/CRX,
реальный WebView2 и чистая установка требуют Windows. Переносимые тесты и
успешная линковка Mac не являются Windows-квалификацией.

Список Windows import libraries сверяется с официальным ObjectARX SDK 2027.
`acgex26.lib` подключается из `utils/brep/lib-x64` вместе с `acbr26.lib`.
Она сохраняет точное преобразование внешних BRep кривых в gelib; расчётный
путь не заменяется приближением. Проверки наличия SDK-входов сохраняются.
Настоящий MSVC прогон также проверяет передачу `/link` и его параметров в одной
строке response file. Общий C++ код явно подключает `<stdexcept>`, а Windows
prefix объявляет `CPoint` для прототипов SDK без подключения MFC runtime.

Общий checkout содержит Windows frozen/build/package/setup pipeline.
Конечному пользователю не нужны SDK, Python, Node или PowerShell. Сборщик
использует квалифицированные зависимости и явно предоставленные prerequisites.
Установщик проверяет bytes/manifest и переключает только собственный bundle;
Workspace и Transfers сохраняются. Перед заменой он проверяет, что текущий
пользователь закрыл AutoCAD, Core, desktop и runtime во всех своих сеансах.
Реальные update/rollback/uninstall и загрузка app-local DLL остаются частью
приёмки на Windows.

## Повторная проверка Windows-установки

Windows preflight проверяет не только AppVersion XML, но и регистрацию единственного
ARX: Win64, AutoCAD R26.0, фиксированный путь, независимую версию GUI, команду
GAOPEN и запуск при старте AutoCAD. XML с Mac-путём или иной версией не проходит
даже после пересоздания собственного manifest. Базовый VC runtime обязателен
как рядом с host, так и в Worker: фоновое задание копирует только Worker.
Включённый offline WebView2 installer и его типизированная квитанция проверяются
при проверке payload, включая размер и SHA; отсутствие ресурсов не откладывается
до установки на чистом компьютере. Подпись Microsoft проверяет машина сборки,
а пользовательский setup сверяет запечатанные байты, без сетевой загрузки.

Установщики одного SID используют общий для всех Windows-сеансов mutex, разные
SID получают разные имена. Это закрывает параллельное обновление из двух сеансов;
проверка закрытых приложений перед rename остаётся отдельной границей. Dangling
ссылка в имени установленного bundle тоже считается занятым чужим объектом и
блокирует откат, а не заменяется. Большой onefile Setup сохраняется блоками;
его EXE и маркер публикуются отдельными атомарными переименованиями после полной
записи. Ошибка записи не оставляет частичный EXE или маркер в окончательном имени,
поэтому штатную операцию можно повторить.

Windowed frozen Setup не полагается на наличие Python stdout/stderr. Диагностика
`--quiet` и `--status-json` пишет UTF-8 в унаследованный pipe через Win32
GetStdHandle/WriteFile, если обычного Python stream нет. При двойном щелчке без
такого канала новая консоль не создаётся. Наличие канала, частичные записи и
освобождение mutex покрыты переносимыми тестами с API-адаптерами; настоящее
наследование pipe и межсеансовое поведение проверяются на Windows.

Основания Win32-границы: [kernel object namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces)
и [CreateMutex](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexa).
Регистрация AutoCAD: [RuntimeRequirements](https://help.autodesk.com/cloudhelp/2027/ENU/AutoCAD-Customization/files/GUID-1591CA01-EF87-48CD-952B-772FE26037F1.htm).

До выпуска нужны физические проверки: MSVC сборка, установка без dev среды,
GUI захват с XREF, подготовка `/3`, ручная/автоматическая посадка, сохранение
и холодное открытие, отдельный CAD-выпуск, WebView2 dirty/unknown/restart,
Blender с пользовательскими ресурсами, отмена и освобождение базы. AutoCAD 2026
проверяется отдельно. Готовый Windows-дистрибутив до этого не заявляется.

`package_preflight.py check-source` сверяет manifest и все перечисленные исходные
файлы до компиляции, в том числе при `ValidateOnly`. Product builder и прямой
runtime builder вызывают одну проверку, а после freezing отдельно проверяется
код PYZ и bootstrap entry. Успех проверки источников не означает выполнения
Win32 или приёмки AutoCAD. Кеши `windows-env.ps1` находятся внутри checkout
в `.runtime/cache/packages`, поэтому подготовка не требует записи в корень диска.
Ошибки CLI-проверки источников сериализуются с ASCII-escape в JSON: вызывающий
процесс может читать машинный результат как UTF-8 при любой консольной кодировке.
Playwright на Windows запускает API через локальный `.venv`, Web через Node и
кладёт тестовую SQLite в `.runtime/tmp`; `E2E_BROWSER_CHANNEL=chrome` выбирает
установленный Chrome. Браузерный набор требует сверки сценариев с актуальным
интерфейсом: при проверке этого checkout прошли 12 из 66 сценариев, многие
остановились на прежних названиях элементов. Один реальный crash при неполном
ответе сцены исправлен и подтверждён повтором его сценария.

Qualification runner допускает новый каталог отчёта вне payload. Сначала
проверяются сам корень комплекта и физическое расположение результата, затем
создаются недостающие каталоги без ссылок/reparse points. Ни alias корня пакета,
ни alias каталога отчёта не разрешают запись внутрь проверяемого комплекта.
Проверки этих отказов и первого запуска используют только синтетические данные.

## Удалённая Windows-сборка с Mac

`.github/workflows/windows-build.yml` запускает ограниченные по времени задания
на настоящем Windows x64 runner. Mac отправляет проверенный commit и получает
журналы MSVC, результаты тестов и SHA бинарников. Workflow использует закреплённые
SHA официальных Actions. WebView2 SDK скачивается из официального NuGet по точной
версии и SHA256 из `windows-ci-inputs.json`; SDK в Git и build artifacts не входит.
`.gitattributes` сохраняет LF для текстовых исходников и на Windows: SHA в
квитанции MSVC можно сверить с теми же файлами исходного комплекта без
нормализации строк. Бинарные CAD fixtures сохраняют исходные байты.

Host job компилирует и линкует WebView2-оболочку, исполняет portable policies
и synthetic Win32 runtime tests, затем запускает собранный host с `--self-test`,
`--build-info` и `--status-json` в отдельных процессах с ограничением времени.
Проверяются JSON-ответы и отсутствие записи в профиль. Диагностический отказ
из-за отсутствующего установленного payload допустим и явно сохраняется в
квитанции. Runtime job готовит Python из lockfile, проверяет
настоящие Win32 handles, Job Objects, SID и загрузку DLL, отдельно компилирует
оконный Setup для диагностического smoke. Этот Setup не устанавливается и не
распространяется как пользовательский продукт. Проверки используют собственные
временные каталоги. Профиль и проекты пользователя не участвуют.
Отдельные тесты внешних запусков проверяют DLL-поиск, окружение Blender,
ожидание превью и очистку классификатора на контролируемых процессах и fixtures.
Пользовательские модели и установленный Blender в этом CI не требуются.

Опциональный `-BuildFrozenApi` собирает настоящий автономный API production builder,
сверяет PYZ и bootstrap с исходниками закреплённого Git commit и проверяет
14 raw-ресурсов, перенос в другую папку, приватный API, health и завершение.
Smoke использует синтетический Web-документ и профиль внутри checkout, без
пользовательской базы, native ticket, AutoCAD или моделей растений. Workflow
сохраняет только журналы, source inventory и квитанции, без frozen payload и
временного профиля. Успех этой границы не означает приёмку полного продукта.

Корень Windows-передачи проверяется как существующий каталог через нативную
цепочку directory HANDLE, включая запрет reparse points у корня и родителей.
Он не передаётся файловому адаптеру как путь `.`; дочерние файлы сохраняют
прежний строгий контракт канонического относительного пути. Проверка корня
ничего не создаёт; прежнее поведение Mac сохраняется.

Для ARX/CRX компиляции достаточно Windows ObjectARX SDK 2027 и MSVC/Windows SDK;
установленный AutoCAD нужен для последующей загрузки и CAD-приёмки. Получение
ObjectARX SDK через лицензионную форму остаётся отдельным входом разработчика.
Runner Windows Server проверяет компиляцию и Win32 границы, а поддерживаемая
Windows 11 с AutoCAD 2027 нужна для сквозной проверки продукта.

Отдельный `windows-native-build.yml` принимает официальный URL Windows ObjectARX
2027 и проверенный SHA256. SDK распаковывается через 7-Zip без запуска его EXE.
`ci-windows-native.ps1` включает MSVC x64, независимо собирает Core CRX и GUI ARX,
проверяет PE exports через `dumpbin` и сохраняет журналы обеих целей. В artifacts
попадают только собственные модули и квитанции, без SDK и Autodesk DLL.
Push этого workflow выполняет регистрацию; native job запускается только вручную
с предоставленными входами. Пропущенное задание не является сборкой.

`windows-product-build.yml` собирает все пять production-компонентов из одного
Git commit и полный пользовательский Setup. Закреплённые входы включают полный
офлайн-установщик WebView2, его SHA256 и проверку подписи Microsoft. SDK служит
только для компиляции и сверки импортов: его файлы не входят в Setup. Проверка
импортов по SDK не подтверждает наличие AutoCAD на машине пользователя.
Локальный `qualify-windows.ps1` читает оба поддерживаемых вида DLL inventory:
проверку по установленному AutoCAD и контракт официального ObjectARX SDK.
Для SDK он сверяет закреплённые SHA import libraries, BuildEvidence обоих native
модулей и фактические PE imports всех файлов пакета. Эта проверка остаётся
проверкой состава; загрузку ARX/CRX в AutoCAD подтверждают отдельно.

После сборки отдельная временная обычная учётная запись запускает настоящий
Setup в синтетическом профиле внутри checkout. Она проверяет установку, ярлыки,
регистрацию текущего пользователя, установленный host и автономный API с
собранным Web, затем повторную установку, откат того же комплекта и удаление
с сохранением контрольных рабочих файлов. Такая проверка не заменяет переход
между разными версиями, интерактивный WebView2, AutoCAD или Blender.
Малые журналы установки сохраняются отдельным artifact до загрузки большого
Setup; квитанция установки привязана к SHA256 конкретного EXE.

Синтетический профиль находится в коротком Unicode-каталоге `П` внутри
выделенного каталога CI с правом записи только для временного SID. Исходный
многоуровневый профиль дал DLL-пути до 277 символов и подтверждённый отказ
загрузки Shapely «The filename or extension is too long». Повторная приёмка
использует короткий профиль; перед запуском API измеряет все фактические пути
DLL Runtime в UTF-16, записывает самый длинный путь и отказывает при длине от
260 символов. Поддержка длинных перенесённых профилей этим не подтверждается.

Проверяющий модуль Setup использует те же 14 raw-ресурсов приложения. Сборщик
включает их в собственный frozen архив установщика дополнительно к данным
вложенного API. После freezing он читает CArchive без запуска EXE и побайтово
сверяет каждый ресурс с исходником; отсутствие либо изменение останавливает
сборку до создания квитанции готового кандидата.

При конфликте с устаревшим системным WebView2 интерактивный Setup предлагает
Windows UAC только для включённого Microsoft installer. Его точный SHA и подпись
Microsoft проверяются; открытый Win32 handle запрещает подмену EXE во время
ожидания UAC. Основной Setup, регистрация и проекты остаются у обычного SID.
Отказ, timeout и всё ещё несовместимая фактическая версия не считаются успехом.
Режим `--quiet` не открывает UAC: для системного prerequisite он возвращает
адресную ошибку. Обнаружение Runtime сначала проверяет HKLM, затем HKCU в том
же порядке, что штатный WebView2 loader.

Полный CI отдельно обновляет системный WebView2 теми же включёнными байтами
Microsoft installer из административного harness и записывает старую и новую
версии. Он исполняет production-проверку подписи, handle, ShellExecuteEx и
ожидание процесса; интерактивный UAC диалог этим не проверяется. Затем настоящий
Setup устанавливается временным обычным пользователем с уже совместимым
WebView2. Эти две квитанции не объявляются холодной per-user установкой Runtime.

`windows-candidate-check.yml` повторяет проверку уже собранного неизменного EXE
с обновлённым CI harness. Он сверяет оригинальный Git/source seal и отклоняет
любую правку продуктового кода; разрешён только явный список файлов диагностики
и описания CI. Квитанция различает Git commit бинарного кандидата и commit
проверяющего harness. При сбое до готовности API сохраняется ограниченный
журнал без приватной READY-строки и токенов.


Расширенная проверка Windows исполняет все существующие API-тесты четырьмя
непересекающимися группами и отдельно полный Web/API-client. Это дополнительный
контроль; он не заменяет обязательные 853 проверки оптимизированного хранилища,
замороженный API и приёмку настоящего Setup. Итог каждого задания различает
ошибку проверки и отказ GitHub сохранить artifacts из-за квоты.

Параметризованные тесты используют короткие идентификаторы для больших bytes
и строк. Pytest помещает текущий nodeid в переменную `PYTEST_CURRENT_TEST`,
поэтому содержимое мегабайтного fixture в идентификаторе нарушало ограничение
Windows на значение переменной окружения. Данные и проверки fixture сохранены.

Побайтовая сверка четырёх собственных геометрических fixtures между Windows x64
и Mac ARM64 при одинаковых Python 3.13.15, Shapely 2.1.2 и GEOS 3.13.1 обнаружила
только отдельные координаты buffer-колец с разницей в один младший разряд float,
не более 5.69e-14 м. Свойства, порядок, решения посадки и callbacks совпали.
Для этих четырёх тестов закреплены точные платформенные SHA; производственные
координаты, допуски и проверки целостности не изменены. Тесты времени жизни
подготовленной геометрии следят за фактическим загрузчиком WKB-снимка;
запрет повторной гидратации проверяет и этот вход, и старый JSON-загрузчик.


Тесты Mac-дескрипторов явно выбирают тестируемую платформу, даже при исполнении
на Windows. Отказ POSIX execute bit в Windows моделируется на границе проверки
доступа: NTFS chmod сам по себе его не воспроизводит. Тесты ленивого live-engine
изолируют конструктор POSIX-клиента и проверяют его единственное создание;
этим не заявляется поддержка POSIX live-очереди на Windows. Расширенный API-прогон
продолжает остальные тесты после ошибки, чтобы собрать полный перечень отказов.


ZIP выпуска фиксирует `ZipInfo.create_system = 3` вместе с существующими
Unix-атрибутами файлов. Иначе Python выбирает ОС-создателя по хосту: payload
остаётся одинаковым, но меняются байты архива и SHA вложенных артефактов.
Фиксация сохраняет прежние Mac-эталоны и делает Windows-выпуск побайтово тем же.
Она не меняет DWG, DXF, имена, права, порядок, время записей или сжатие.


Диагностика Windows показала, что быстрые изменения файла того же размера могут
сохранить одновременно LastWriteTime и ChangeTime. Поэтому PreparedStore на
Windows связывает подтверждённый File ID с SHA полных байтов и сверяет содержимое
при повторном использовании. Первичное чтение payload и его SHA удерживает один
HANDLE, запрещающий запись и замену файла. Производный WKB-ресурс передаёт уже
проверенный SHA источника; ошибка также запоминается вместе с SHA повреждённых
байтов, чтобы восстановленный файл распознавался при совпавших временах.

Хеширование идёт ограниченными порциями с отменой операции, без разбора JSON
и без удержания его второй копии. Оно добавляет чтение файла на Windows;
порционный расчёт продолжает переиспользовать свой read_scope. Маковская проверка
отпечатков и SHA-форматы сохранённых проектов не меняются.


Windows PreparedStore.read_scope закрепляет проверенный источник на ограниченный
шаг поиска и запрещает его запись/замену до выхода. Вложенные вызовы проверяют
удержанный File ID без повторного SHA и обхода каталогов на каждую точку.
Роутер сочетает этот guard с существующим read_scope WKB-ресурса; после порции
проверяются оба удержанных дескриптора и пути. Вне guard SHA остаётся обязательным.


Внутри Windows read_scope повторные проверки PreparedStore используют уже
закреплённый HANDLE. Проверенный полный путь удерживается от переименования
и замены на всё время порции; повторный обход каталогов выполняется на границах,
а не на каждую точку. Вне порции сохраняются полный обход пути и проверка SHA.
Обязательный Windows timeout 45 секунд на тест не увеличивается.


CI подтверждает graceful shutdown по коду лидера 0 и пустому собственному Job
в пределах одного срока: 20 секунд для установленного API, 15 для перенесённого.
Он ограниченно дочитывает stdout и ожидает естественный выход потомков, не
используя terminate/close для получения PASS. При отказе различаются старый API119
и новый API, код завершения и число процессов; приватная READY-строка скрывается.
Сборка продукта предварительно проверяет сам этот harness, включая живой Windows Job.

Ручной запуск полного Windows workflow может включать `publish_draft`. После всех
установочных этапов он выгружает тот же Setup, инструкцию, пример внешних ресурсов,
квитанции и SHA256SUMS в новый черновик релиза рабочего `green-atlas-dev`.
Выгрузка разрешена только с `codex/windows-optimized-121`; проверяются commit,
имя, размер и SHA установщика. Ошибка приёмки не допускает выгрузку. Черновик
создаётся до сохранения Actions artifacts, поэтому отдельная квота этого
хранилища не мешает получить файл. Автоматической публикации релиза нет;
его статус и ограничения проверяются перед выпуском. SDK, исходные растения
и журналы сборки в набор release assets не входят.
Обычная приёмка и сборка для черновика имеют отдельные concurrency-группы:
начало выдачи файла не отменяет уже выполняющийся проверочный прогон.
